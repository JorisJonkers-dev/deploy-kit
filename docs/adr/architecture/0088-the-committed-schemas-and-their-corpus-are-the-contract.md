# The committed JSON Schemas and their accept/refuse corpus are the contract, and byte equality only proves the generator's output is committed

A committed JSON Schema is what a reader outside this repository depends on,
and each one is held to a hand-written corpus of documents it must accept and
documents it must refuse. The model the schema is generated from gives the same
verdict on every case. Any implementation, today's or a later one, conforms by
agreeing with the corpus, not by writing the same bytes. The check that
regenerating a schema produces no diff stays, and proves only that the current
generator's output is the one committed.

## Rests on

The middle layer is a contract between the steps that write it and the readers
that consume it ([0003](../model/0003-three-model-pipeline.md)), and its
published schemas are how a reader outside this repository holds a document to
that contract.

**False if:** a committed schema and its model disagree on a document and no
corpus case fails, or a schema can express a kind of break its corpus has no
refused case for and the corpus test stays green. **Settled by:** the corpus
test failing on the published Resolved Application schema with its release-gate
conditional removed, which it does.

## Why

**The schema is already read outside this repository.** The in-cluster
delivery services generate their types from the published schemas
(JorisJonkers-dev/deploy-kit#195). What they rely on is which documents the
schema accepts and which it refuses, not its layout.

**A byte check proves the wrong thing for a second producer.** Another
generator, in this language or another, orders `$defs`, names definitions and
spells conditionals its own way. Requiring the same bytes would tie every
future implementation to zod's output; requiring the same verdicts ties it to
what readers see.

**A generator can silently state less than the model.** zod drops a
refinement when it generates a schema, so until
JorisJonkers-dev/deploy-kit#223 the published Resolved Deployment schema
accepted documents the model refused, and the byte check stayed green. Only a
test that puts the same document to both catches that.

**Committed and hand-written, like every oracle.** A corpus regenerated by an
implementation would agree with that implementation by construction
([0068](0068-two-implementations-meet-at-the-parity-table.md)).

## Alternatives

| option | cost if taken | why rejected |
|---|---|---|
| Keep byte equality as the only check | nothing to write | proves the generator ran, not what a reader sees, and missed the dropped refinement |
| Compare two schemas structurally, ignoring order | no corpus to maintain | two schemas can differ structurally and agree on every document, or match structurally and differ in meaning |
| Validate only the committed oracle documents | already in place for the Resolved Deployment | covers acceptance only: a schema that accepts everything passes |
| Generate the corpus from the model | no hand-written cases | the model becomes its own oracle |

## Reversibility

Undo cost today: one test and seven corpus files, an hour. Becomes costly
once a second implementation is built against the corpus rather than against
zod's output.

## Consequences

- A schema change lands with the corpus cases that prove it, in the same pull
  request, and a schema whose corpus misses a kind of break it can express
  fails.
- A rule the model states and the schema cannot is found by the corpus, not by
  review; [RULE-073](../../architecture-rules.md) keeps such a rule from being
  written in the first place.
- A validator other than Ajv reading the committed schemas needs only standard
  draft 2020-12 plus two annotation keywords, which the contract names.
