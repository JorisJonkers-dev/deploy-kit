\section{Purpose of the Project}
\label{sec:purpose}

\subsection{Goals}
\label{sec:goals}

The project turns short deployment documents into the Kubernetes files that
deploy applications to an existing small cluster. Each \texttt{Application}'s repository holds one
\texttt{Project Intent} document that states what the \texttt{Application}
needs: its \texttt{Process}es, their memory and CPU limits, the ports they
expose, the \texttt{Application}s they depend on, and the routes that reach
them from outside. One \texttt{Platform Intent} document states what all
\texttt{Application}s share: cluster entry points, health-check timings and
backup policies. Task~1 defined the Ecore metamodels for both. The source
metamodel covers the authored documents. The target metamodel covers the
\texttt{Resolved Deployment}: every value the platform derives for an
\texttt{Application}, and the file path each value writes to.

Task~2 builds the model-to-model transformation from source to
\texttt{Resolved Deployment}. Its inputs are the \texttt{Project Intent} and
\texttt{Platform Intent} models of every project in the cluster and the
documents other processes publish; it outputs one
\texttt{Resolved Deployment} per project for Task~3 to consume. The
transformation makes the specification's derivation rules executable: every
value in a \texttt{Resolved Deployment} is produced by a rule, and no author
writes any value by hand.

The transformation has three goals. First, it must derive the same
values as the TypeScript production implementation, which deploys the actual
cluster. Both implementations run against the same oracle files and must
produce identical results. Second, it must stop with an error message when it
cannot derive a value, because a \texttt{Resolved Deployment} with a missing or
fabricated value would look valid yet deploy the wrong configuration.
Third, its output must be complete enough that the Task~3 templates only write
values into their fixed positions. Any path, port or name chosen inside a
template would hide a derivation from review.

\subsection{Role of the Transformations}
\label{sec:role}

Figure~\ref{fig:pipeline} shows the pipeline. Xtext converts each document
to a source model, and the Task~1 OCL constraints reject invalid ones. Three
QVT-Operational transformations then run in sequence.

The first transformation, the lowering, copies declarations made once for an
entire \texttt{Project} or \texttt{Application} down onto each \texttt{Process}.
Its output is the \texttt{Effective Intent}, which still conforms to the
source metamodel. Although it was implemented in Task~1, it was not reported
there, so Section~\ref{sec:lowering} covers it here. The second
transformation, the resolution, reads the lowered models and the
\texttt{Pinned input set}, then writes one \texttt{Resolved Deployment} per
project. It is the main subject of this report. The third, the estate pass,
runs once over all \texttt{Resolved Deployment}s produced together and adds
the files that do not belong to any single project (Section~\ref{sec:estatepass}).

A small Java exporter writes the resolved dependency edges as JSON for
comparison against the oracle. The Acceleo templates of Task~3 then read the
\texttt{Resolved Deployment}s and generate the Kubernetes files.

\subsection{Refinement of Tasks 0 and 1}
\label{sec:refinement}

Task~0 treated the
node contract, images lock and snapshot as plain inputs, while Task~1 only
modelled the two authored documents. The resolution needs these as models, so
a third metamodel now describes the \texttt{Pinned input set}, with its own
Xtext grammar for each document (Appendix~\ref{app:pinned}). This metamodel
lives in a separate package because no project author writes these documents.

Task~1 described three stages: authored, resolved and generated text. The
lowering adds a fourth stage between authored and resolved, so each rule in
the resolution reads values from a single level
(Section~\ref{sec:twotransformations}).

Task~1 planned one resolved model for the entire cluster, because edges,
routes and reverse dependencies require a cluster-wide view. Every run
still reads every project. The output is now one
\texttt{Resolved Deployment} per project, because the production
implementation and the oracles are per project
(Section~\ref{sec:perproject}); the per-\texttt{Application} projection from
Task~1 is still present as the \texttt{ResolvedApplication} inside that
model. The estate pass adds the one job that no single project's resolution
can compute (Section~\ref{sec:estatepass}).

Task~1's target metamodel only had a worked example for \texttt{minimal}. The
other examples needed additional concepts: migrations, backup identities, API
access, sidecar containers and twelve more file types. Appendix~\ref{app:metamodels}
lists every change.

\subsection{Assumptions and Conditions}
\label{sec:assumptions}

The transformation assumes four conditions.

\begin{itemize}
  \item \textbf{Valid input.} The Task~1 OCL constraints reject an invalid
    source model before the lowering runs, checking the entire document set
    of a run. A stop in the transformation is a safety net for facts the
    constraints do not yet cover (Section~\ref{sec:stops}).
  \item \textbf{One cluster per run.} A run reads one \texttt{Platform Intent}
    and one node contract, both naming the same cluster. All concepts,
    examples and oracles derive from that single existing cluster.
  \item \textbf{The production implementation's choices.} Where the
    specification allows a choice, the transformation decides as the
    production TypeScript implementation does.
  \item \textbf{No live cluster access.} The transformation only reads the
    documents provided to it. Any fact known only to a running cluster, such
    as which node holds a particular volume, must arrive via the
    \texttt{ClusterState} snapshot captured by another process.
\end{itemize}

\paragraph{More Than One Cluster.} The current implementation targets a
single cluster, and every cluster-specific element is already a run input: the
\texttt{Platform Intent}, the node contract and the \texttt{ClusterState}
snapshot each name their cluster, and a \texttt{Project}'s environment files
use a shared base plus a per-cluster overlay that the resolution selects via
the \texttt{Platform Intent} cluster name (Section~\ref{sec:placeholders}).
Supporting a second cluster would therefore need a second run over that
cluster's own three documents, and two additions beside it: a
\texttt{Project Intent} would need to declare which clusters it targets, and
the network policy of an edge to another cluster would need to allow an
address range rather than a specific pod address. Such an edge would resolve
through the \texttt{Platform Intent} external provider list, as the current
edge from \texttt{auth} to an external mail server already does
(Section~\ref{sec:edgerule}).
