\section{Purpose of the Project}
\label{sec:purpose}

\subsection{Goals}
\label{sec:goals}

The project generates the Kubernetes files of a small cluster from short
deployment documents. Each application's repository holds one \emph{project
document}. It says what the application needs: its processes, their memory and
CPU, the ports they offer, the services they depend on, and how outside traffic
reaches it. One \emph{platform document} says what all applications share, such
as the cluster's entry points, its health-check timings and its backup
policies. Task~1 defined the metamodels for both in Ecore, the metamodelling
language of the Eclipse Modeling Framework (EMF). The \emph{source metamodel}
describes the two documents. The \emph{target metamodel} describes the
\emph{resolved model}: every value the platform derives for an application, and
the file each value will be written to.

Task~2 builds the model-to-model transformation from source models to resolved
models. It reads the source models of every project in the cluster, the platform
document, and a few documents that other processes publish. Its output is the
resolved model of one project, which the code generation of Task~3 reads. The
transformation is where the derivation rules of the specification become
executable: every value in a resolved model comes from a rule in the
transformation, and no author writes those values by hand.

The transformation has three goals.

\begin{enumerate}
  \item \textbf{Same decisions as production.} It derives the same values as
    the production implementation of the same specification, which is written
    in TypeScript and deploys the cluster. Both implementations are tested
    against the same committed result files, called \emph{oracles}.
  \item \textbf{No silent defaults.} It stops with a message when it cannot
    derive a value. A resolved model with a missing or invented value would
    generate files that look valid and deploy the wrong thing.
  \item \textbf{Nothing left to the templates.} Its output is complete enough
    that the templates of Task~3 only write values out. A template that had to
    choose a path, a port or a name would hide a derivation from every check.
\end{enumerate}

\subsection{Role of the Transformations}
\label{sec:role}

Figure~\ref{fig:pipeline} shows the pipeline. Xtext turns each document into a
source model, and the OCL constraints of Task~1 reject invalid models. Three
QVT-Operational (QVTo) transformations then run in a chain.

\begin{enumerate}
  \item The \emph{lowering} copies what an author declared once for a whole
    project or application onto each process. Its output, the \emph{Effective
    Intent}, uses the source metamodel too. It was part of the Task~1
    implementation but not of the Task~1 report, so Section~\ref{sec:lowering}
    describes it.
  \item The \emph{resolution} reads the lowered models and the pinned inputs and
    writes one resolved model. It is the main subject of this report.
  \item The \emph{estate pass} runs once over the resolved models of all
    projects generated together. It adds the files that belong to no single
    project (Section~\ref{sec:estatepass}).
\end{enumerate}

A small Java exporter writes the resolved dependency edges as JSON, which is
compared with the oracle. The Acceleo templates of Task~3 read the same
resolved models and write the Kubernetes files.

\subsection{Refinement of Tasks 0 and 1}
\label{sec:refinement}

Writing the transformation refined the earlier tasks in five ways.

\begin{itemize}
  \item \textbf{The pinned inputs became models.} Task~0 listed the node
    contract, the images lock and the snapshot as inputs the generator is
    given, and Task~1 modelled only the two authored documents, stating that
    only those have metamodels. The resolution needs the pinned inputs as
    models, so a third metamodel now describes them, with an Xtext grammar per
    document (Appendix~\ref{app:pinned}). It is a separate package because no
    project author writes these documents.
  \item \textbf{A lowered stage.} Task~1 named three stages: authored,
    resolved and generated text. The lowering adds a fourth between the first
    two, so that each rule of the resolution reads one level of values instead
    of three (Section~\ref{sec:twotransformations}).
  \item \textbf{One resolved model per project.} Task~0 ran each generator once
    over all projects, and Task~1 planned one resolved model for the whole
    cluster, because edges, routes and reverse dependencies need a cluster-wide
    view. That view is kept: every run still reads every project. Only the
    output is per project, because the production implementation writes one
    resolved document per project and the oracles are per project
    (Section~\ref{sec:perproject}). Task~1's per-application \emph{projection}
    is still the \texttt{ResolvedApplication} inside that model.
  \item \textbf{An estate pass.} One generated job, which writes every
    project's secret-store policies, is named after a digest over all of them.
    No single project's resolution can compute that name, so a small second
    transformation over all resolved models plans the job.
  \item \textbf{The target metamodel grew.} Task~1's target metamodel had a
    worked instance only for \texttt{minimal}. The other examples need more:
    migrations, backup identities, API access, sidecar containers, and twelve
    more kinds of generated file. Appendix~\ref{app:metamodels} lists every
    change.
\end{itemize}

\subsection{Assumptions and Conditions}
\label{sec:assumptions}

\begin{itemize}
  \item \textbf{The input is valid.} The OCL constraints reject an invalid
    source model before the lowering runs, over the whole set of documents of
    the run. A stop in the transformation is a safety net: it fires only for a
    fact the constraints do not check yet (Section~\ref{sec:stops}).
  \item \textbf{One cluster per run.} Each run reads one platform document and
    one node contract, and both name one cluster. The concepts, the examples
    and the oracles all come from one existing cluster.
  \item \textbf{The production implementation is the reference.} Where the
    specification leaves a choice, the transformation makes the same choice as
    the production implementation, so that both produce the same oracles.
  \item \textbf{No live cluster access.} The transformation reads only the
    documents it is given. Facts that only a running cluster knows, such as
    which machine holds a volume, arrive through the snapshot, which another
    process captures.
  \item \textbf{Runs without Eclipse.} The build runs the transformations with
    QVTo's standalone executor on every change. Eclipse run configurations also
    run them (Appendix~\ref{app:handin}).
\end{itemize}

\paragraph{More Than One Cluster.} The single cluster is a choice of scope,
not a limit of the structure. Everything specific to a cluster is already an
input of the run: the platform document, the node contract and the snapshot
each name their cluster, and a project's environment files are a shared base
plus an overlay per cluster, which the resolution selects by the platform's
cluster name (Section~\ref{sec:placeholders}). A second cluster would therefore
be a second run with that cluster's three documents. Two things would be new,
and neither is built or tested:

\begin{itemize}
  \item a project document would have to say which clusters it runs in;
  \item an edge to a service in another cluster would resolve through the
    platform's list of external providers, as the edge from \texttt{auth} to a
    mail server outside the cluster already does
    (Section~\ref{sec:edgerule}), but its network policy would have to admit
    an address range instead of a pod.
\end{itemize}
