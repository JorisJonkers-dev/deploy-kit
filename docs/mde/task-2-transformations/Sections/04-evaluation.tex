\section{Tests and Evaluation}
\label{sec:evaluation}

The transformations are tested by running them on eight examples and comparing
their output with oracle files: the expected outputs committed with the
specification's worked examples. Matching them shows the transformation
derives the values the specification expects.

The build runs six test types on every change.

\begin{itemize}
  \item \textbf{Flattened models.} For the four examples with shared
    declarations, the flattened model is written as JSON and compared
    byte-for-byte with the expected flattened model.
  \item \textbf{Dependency edges.} For each example, the resolved edges are
    exported as JSON and compared byte-for-byte with the expected file. These
    tests read only files the pipeline wrote, so they check the pipeline as a
    user would run it.
  \item \textbf{Revisions.} Each expected resolved file records its
    \texttt{Revision}, a digest of the \texttt{Application} element in
    the specification's canonical JSON form. A matching \texttt{Revision}
    checks the values included in that representation
    (Section~\ref{sec:revisionevidence}). The digest covers the element's own
    decisions, not the whole resolved model: the path plan, the network
    policies and the Vault documents fall outside it, which is what the
    complete-model and generated-file comparisons below are for.
  \item \textbf{Complete expected models.} \texttt{minimal} and
    \texttt{secrets} have full expected \texttt{Resolved Deployment} models,
    compared using EMF's structural equality (\texttt{EcoreUtil.equals}),
    which checks every attribute and reference.
  \item \textbf{Generated files.} Tests run the Task~3 templates on the
    transformation output and compare every generated file with its committed
    counterpart. This checks the resolved values used by the templates as
    well as their serialization.
  \item \textbf{Interface tests.} JUnit tests check that the resolution
    accepts a minimal \texttt{Project}, rejects a \texttt{Project} absent
    from the input, and reports the file name when a configuration file is
    missing. Final-pass tests check that one Vault policy job covers two
    \texttt{Project}s, its name changes when a document changes, no job is
    generated without documents, and conflicting job definitions abort the
    run. Eight flattening cases check the merging of shared declarations.
\end{itemize}

The coverage and mutation tools measure the Java integration code, which
must reach full line and branch coverage and a 100\% mutation score. They
cannot measure QVTo. The checks above therefore provide functional evidence
for the transformation rules, without establishing QVTo branch coverage.

\subsubsection{Revision Evidence}
\label{sec:revisionevidence}

An \texttt{Application}'s \texttt{Revision} is the hash of its canonical
JSON representation. This includes its \texttt{Process}es with image,
user, deadline, probes, placement, secrets, volumes, backups, environment and
edges; its \texttt{Exposure}s and routes; its \texttt{Release Gate}, the service that holds the switch until every
\texttt{Process} is healthy; and its migration.

The transformation builds that text from its own \texttt{Resolved Deployment}
(Section~\ref{sec:blackbox}), so one different value, one extra environment
variable or one different order changes the digest. Ten \texttt{Application}s
across five examples have a \texttt{Revision} in an expected file, and all
ten match.

For these \texttt{Application}s, one digest comparison checks nearly every
derived value in the element. A further test checks that the digest responds
to deployment decisions: increasing memory in \texttt{minimal} from 256Mi
to 512Mi changes the \texttt{Revision}, whereas changing only the capture
time of the cluster-state snapshot leaves it unchanged.

\subsubsection{Generated-File Evidence}
\label{sec:treeevidence}

An \texttt{Application}'s \texttt{Revision} excludes network policies,
Vault documents and file paths. Comparing generated files checks these
parts of the output as well: an incorrect allowed peer or destination path
would fail the comparison even if the \texttt{Revision} matched. Across
five examples and the cluster-wide output, all 167 committed files are
reproduced byte-for-byte, including the final-pass job files.

\subsubsection{Gaps in the Evidence}
\label{sec:thin}

Two examples, \texttt{edge} and \texttt{observability}, have no
\texttt{Revision}, no committed generated files and no expected model. Their
\texttt{dependencies.json} files list no dependency edges. Evidence for
these examples is therefore limited to successful execution and the
comparisons for other examples that use their proxies and collectors. Those
comparisons check the values consumed by other projects, but leave the
remaining proxy and collector configuration unchecked.

The expected \texttt{secrets} model was obtained by reviewing the generated
output rather than constructing an independent oracle. It detects later
changes to that output, but agreement does not independently establish
correctness. The review found a gap in the specification: the Secret Store
network policy allows no inbound traffic, although holders of secrets are
allowed to send traffic to it. If enforced, the receiving policy would
still block those connections; permission on the sending side is insufficient.

The hand-written model of \texttt{minimal} from Task~1 was updated after
hand-in to follow the metamodel changes of Appendix~\ref{app:target}. Its
\texttt{Revision} was copied from the oracle, so that field no longer
provides an independent check.

\subsubsection{Defects Found}
\label{sec:defects}

Comparisons found a defect no single example had shown: the path plan
placed cluster-wide route files under \path{apps/edge/}, which is also the
directory of the \texttt{Project} named \texttt{edge}. The \texttt{edge} \texttt{Project}'s files would
have mixed with routes from every other \texttt{Project}. The fix moved all
cluster-wide files under \path{estate/}, in the specification's path rules
and in the path plan, and the
committed files now hold each file at its correct path.

\subsection{Limitations}
\label{sec:limitations}

Agreement with the oracles supports the transformation's conformance to
their expected outputs. It does not establish that the oracles or the
specification are correct. Only the hand-written model of \texttt{minimal}
was constructed directly from the specification.

The eight examples exercise every derivation rule, but a matching result
for one input does not prove that every branch of that rule works. The
\texttt{knowledge} example, which models a \texttt{Project} being retired, is
not one of them; its successor \texttt{knowledge-platform} is.

Most cross-document checks have moved into OCL constraints. The remaining
checks abort the transformation at the first problem and report no source
location. The cross-document constraints still use \texttt{allInstances()};
the planned change to navigate from a single root object is not yet
implemented.

QVTo caches mapping results but not query results. Lookups such as
\texttt{edgeOf} and \texttt{Surface} address resolution are therefore
repeated wherever they are used. Several queries scan all
\texttt{Process}es for each \texttt{Process}, giving quadratic growth in
work. For much larger inputs, measurements would be needed to identify
queries worth replacing with cached mappings or precomputed properties.

Placement produces a list of eligible nodes for each \texttt{Process};
Kubernetes chooses the actual node. Each eligibility check considers that
\texttt{Process} in isolation, so several may be eligible for a node even
though their combined requests exceed its capacity.

When two \texttt{Process}es provide the same \texttt{Surface}, name order
determines which is selected. Ordering between \texttt{ReconcileUnit}s is
defined at \texttt{Project} granularity because Flux orders these groups of
files as whole units; individual \texttt{Application}s within a unit
cannot be ordered separately.

The transformation computes provenance digests from the EMF representation
of the inputs. This differs from the representation specified for the
oracles, so those digests do not match. The digests used in generated files
do match: the \texttt{Revision}, configuration-file name digests and the
Vault policy job name.

Automated tests use the standalone executor. The Eclipse launch
configuration and \texttt{plugin.xml} registration have only been checked
manually.

\subsection{Reflection}
\label{sec:reflection}

QVTo handled the two main kinds of reference used by the transformation.
OCL queries searched all projects to find dependency providers; the mapping
trace linked routes to the resolved \texttt{Process}es already created for
them. This avoided maintaining a separate lookup table. The caller could
also control when each operation ran, creating processes before their routes
and computing revisions last. Repeated lookups were left unoptimised
because performance was outside the scope of this proof of concept.

The greatest effort went into reproducing the \texttt{Revision}. The
target model has a different structure from the specification's JSON, so
the transformation had to reconstruct the specified field
names, omissions and ordering before hashing. That reconstruction occupies
about one sixth of \texttt{resolution.qvto}. A hash mismatch could mean
either a wrong deployment decision or a wrong JSON representation, with no
indication of where they differed. A better test design would compare that
JSON directly before checking its digest, separating derivation errors from
serialization errors. Using a Java hash function saved little of this
work: most of the code was needed to construct the JSON in OCL.

Test evidence should also have been planned alongside the examples.
\texttt{secrets} and \texttt{knowledge-platform} could run successfully
before their output comparisons were added; execution alone did not reveal
which derived values were wrong. Each example should have an expected
result before it is used as evidence. Copying the oracle's
\texttt{Revision} into the adapted Task~1 model meant
that field could no longer expose a mistake in the oracle. Retaining the
original model and documenting the adapted fields would make that loss of
independent evidence explicit.
