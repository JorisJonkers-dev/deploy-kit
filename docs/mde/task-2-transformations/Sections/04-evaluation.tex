\section{Tests and Evaluation}
\label{sec:evaluation}

The transformations are tested by running them on eight examples and comparing
their output with expected files. Most expected files come from the production
implementation processing the same documents, and both implementations run
generating the same oracles.

Six test types answer different questions, and the build runs all of them on
every change.

Lowered models: for the four examples with shared declarations, the lowered
model is written as JSON and compared byte-for-byte with the expected
Effective Intent.

Dependency edges: for each example, the resolved edges are exported as JSON and
compared byte-for-byte with the expected file. These tests only read files the
pipeline wrote, verifying the pipeline as a user would run it.

Revisions: each expected resolved file records its revision, a digest over the
Application's complete element. Equal revisions confirm every value matches
(Section~\ref{sec:revisionevidence}).

Complete expected models: minimal and secrets have full expected Resolved
Deployment models, compared using EMF's structural equality (EcoreUtil.equals),
which checks every attribute and reference.

Generated files: since Task~3 templates decide nothing, a wrong value in a
Resolved Deployment becomes a wrong byte in a generated file. Tests generate
the files from the transformation output and compare each with the committed
output.

Interface tests: JUnit tests run each transformation on models built in code.
The resolution is tested with the smallest project that resolves, a project
not in the input, and an Asset whose file is missing which must stop with
the file name. The estate pass is tested with one job planned over two
projects, a job name that moves when a document changes, no job without
documents, and two projects that disagree. The lowering is tested with eight
cases of merging shared declarations.

The Java code around the transformations must reach full line and branch
coverage and a 100% mutation score. These tools cannot measure QVTo, so the
QVTo code is verified only by the comparisons above.

\subsubsection{What the Revisions Show}
\label{sec:revisionevidence}

An Application revision is the digest of its whole element as the production
implementation writes it: its Processes with image, user, deadline, probes,
placement, secrets, volumes, backups, environment and edges; its Exposures and
routes; its ReleaseGate and migration.

The transformation builds that text from its own Resolved Deployment
(Section~\ref{sec:blackbox}), so one different value, one extra environment
variable or one different order changes the digest. Ten Applications across five
examples have a revision in an expected file, and all ten match.

For these Applications, the revision check verifies nearly every value at once,
a task a hand-written model could not achieve with the same effort. A further
test confirms the revision moves for the right reasons: raising minimal memory
from 256Mi to 512Mi changes it, but changing the snapshot capture time, which
decides nothing, does not.

\subsubsection{What the Generated Files Show}
\label{sec:treeevidence}

Values no revision covers, such as the path plan, network policies and Vault
documents, still appear in generated files. 167 committed files across five
examples and the cluster-wide tree, including the estate pass job, are
reproduced byte-for-byte. The same inputs always produce the same bytes.

\subsubsection{Where the Evidence Is Thin}
\label{sec:thin}

Two examples, edge and observability, have no revision, no committed tree and
no expected model. Their edge files are empty. For them, the evidence is that
the run succeeds and that other examples, which look up their proxies and
collectors, reproduce their expected files.

The secrets model is a reviewed output rather than an independent oracle. It
catches any later change, and the review itself found one gap in the
specification: the Secret Store network policy admits nobody inbound even
though every holder of a Secret may send to it.

The hand-written model of minimal from Task~1 was updated after Task~1 to
follow the metamodel changes of Appendix~\ref{app:target}. Its revision was
taken from the production implementation, so one field no longer checks
independently.

\subsubsection{Defects Found by Testing}
\label{sec:defects}

Comparisons found defects no single example would reveal. The clearest: the
path plan placed cluster-wide route files under apps/edge/, which is also the
directory of the project named edge. The edge example's files would have mixed
with routes from every other Project. The fix moved all cluster-wide files under
estate/, in both implementations, and the committed trees now hold each file
at its correct path.

\subsection{Limitations}
\label{sec:limitations}

The oracles come from another implementation. Agreement shows two
implementations of the specification decide the same, not that the
specification itself is correct. Only the hand-written model of minimal was
written directly from the specification.

Eight examples form a sample. They demonstrate every rule runs and agrees on
these inputs, not that each rule is correct in every case. The QVTo code is not
mutation-tested.

Checks across documents are stops, not diagnostics. A stop reports one problem
without its document location. Most such checks moved into constraints; the
remaining stops are a safety net. The cross-document constraints still use
allInstances(); moving them onto one root object is decided but not implemented.

Queries are recomputed. QVTo caches mapping results but not queries, so
edgeOf or a Surface address is recomputed wherever used. Several queries scan
every Process in the cluster, so work grows with the square of Process count.
Parsing, checking, lowering, resolving and writing all eight examples takes
about 17 seconds. For much larger clusters, hot queries would become mappings
or precomputed properties, measured first.

Capacity is checked per machine. A Process is eligible for a machine that can
hold it alone. The resolution does not sum what all Processes request of one
machine.

Two small modelling choices remain. When two Processes provide the same
Surface, the first in name order wins. The order between ReconcileUnits is per
Project, not per Application, because Flux orders whole units.

Provenance digests differ by design. Input digests are hashes over each
implementation's own model form. Every digest reaching a generated file—the
revision, an Asset name, the policy job name—is reproduced.

The knowledge example is not resolved. It models a Project being retired.
Its successor, knowledge-platform, is.

The Eclipse run configuration is not tested. The build uses the standalone
executor. The configuration and plugin.xml registration are only run manually.

\subsection{Reflection}
\label{sec:reflection}

The largest single piece is not a derivation but the revision. Writing the
production implementation's JSON form of an Application in OCL, key by key, takes
about one sixth of resolution.qvto. Every mistake shows only as a different
hash. It was worth the effort: once the revisions matched, they verified nearly
every value of ten Applications simultaneously, which a second hand-written model
could not achieve for the same work.

QVTo fitted the work well. Most rules are queries over the whole cluster,
which OCL expresses naturally. The explicit trace made every reference between
created elements visible. Three language details cost time.

resolve, from and access are keywords, so the black-box unit is not named after
its Java package, and two metamodel features are written \texttt{\_from} and \texttt{\_access}.

A multi-statement if needs braces.

Inside an object expression, result still refers to the enclosing mapping result,
not the object being created.

With hindsight, the evidence would have been planned with the examples. The
expected model of secrets and the parity checks for knowledge-platform were only
added at the end, when a review asked which examples had no comparison. The Task~1
model of minimal should have been kept unchanged beside the updated one, so the
one independent oracle would remain independent.
