\section{Tests and Evaluation}
\label{sec:evaluation}

The transformations are tested by running them on eight examples and comparing
their output with oracle files. The oracles come from the production
implementation processing the same input documents, so matching them shows
both implementations derive the same values.

Six test types answer different questions, and the build runs all of them on
every change.

Lowered models: for the four examples with shared declarations, the lowered
model is written as JSON and compared byte-for-byte with the expected
Effective Intent.

Dependency edges: for each example, the resolved edges are exported as JSON and
compared byte-for-byte with the expected file. These tests only read files the
pipeline wrote, verifying the pipeline as a user would run it.

Revisions: each expected resolved file records its \texttt{Revision}, a
digest over the \texttt{Application} complete element. Matching
\texttt{Revision}s confirm that the same values were derived
(Section~\ref{sec:revisionevidence}).

Complete expected models: \texttt{minimal} and \texttt{secrets} have full
expected \texttt{Resolved Deployment} models, compared using EMF's structural
equality (\texttt{EcoreUtil.equals}), which checks every attribute and
reference.

Generated files: since Task~3 templates decide nothing, a wrong value in
a \texttt{Resolved Deployment} becomes a wrong byte in a generated file. Tests
generate the files from the transformation output and compare each with the
committed output.

Interface tests use JUnit. The resolution is tested with the smallest
project that resolves, a project not in the input, and an \texttt{Asset} whose
file is missing which must stop with the file name. The estate pass is
tested with one job planned over two projects, a job name that moves when a
document changes, no job without documents, and two projects that disagree.
The lowering is tested with eight cases of merging shared declarations.

The Java code around the transformations must reach full line and branch
coverage and a 100% mutation score. These tools cannot measure QVTo, so the
QVTo code is verified only by the comparisons above.

\subsubsection{What the Revisions Show}
\label{sec:revisionevidence}

An \texttt{Application} \texttt{Revision} is the digest of its whole element
as the production implementation writes it: its \texttt{Process}es with image,
user, deadline, probes, placement, secrets, volumes, backups, environment and
edges; its \texttt{Exposure}s and routes; its \texttt{Release Gate} and
migration.

The transformation builds that text from its own \texttt{Resolved Deployment}
(Section~\ref{sec:blackbox}), so one different value, one extra environment
variable or one different order changes the digest. Ten \texttt{Application}s
across five examples have a \texttt{Revision} in an expected file, and all
ten match.

For these \texttt{Application}s, the \texttt{Revision} check verifies nearly
every value at once, a task a hand-written model could not achieve with the
same effort. A further test confirms the \texttt{Revision} moves for the
right reasons: raising \texttt{minimal} memory from 256Mi to 512Mi changes it,
but changing the snapshot capture time, which decides nothing, does not.

\subsubsection{What the Generated Files Show}
\label{sec:treeevidence}

Values no \texttt{Revision} covers, such as the path plan, network policies
and Vault documents, still appear in generated files. 167 committed files
across five examples and the cluster-wide tree, including the estate pass job,
are reproduced byte-for-byte. The same inputs always produce the same bytes.

\subsubsection{Where the Evidence Is Thin}
\label{sec:thin}

Two examples, \texttt{edge} and \texttt{observability}, have no
\texttt{Revision}, no committed tree and no expected model. Their edge files
contain no edges. For them, the evidence is that the run succeeds and that
other examples, which look up their proxies and collectors, reproduce their
expected files.

The \texttt{secrets} model is a reviewed output rather than an independent
oracle. It catches any later change, and the review itself found one gap in
the specification: the Secret Store network policy admits nobody inbound
even though every holder of a Secret may send to it.

The hand-written model of \texttt{minimal} from Task~1 was updated after
Task~1 to follow the metamodel changes of Appendix~\ref{app:target}. Its
\texttt{Revision} was taken from the production implementation, so one field
no longer checks independently.

\subsubsection{Defects Found by Testing}
\label{sec:defects}

Comparisons found a defect no single example would reveal: the path plan
placed cluster-wide route files under \path{apps/edge/}, which is also the
directory of the project named \texttt{edge}. The \texttt{edge} example's files would
have mixed with routes from every other \texttt{Project}. The fix moved all
cluster-wide files under \path{estate/} in both implementations, and the
committed trees now hold each file at its correct path.

\subsection{Limitations}
\label{sec:limitations}

The oracles come from another implementation. Agreement shows two
implementations of the specification decide the same, not that the
specification itself is correct. Only the hand-written model of minimal was
written directly from the specification.

Eight examples form a sample. They demonstrate every rule runs and agrees on
these inputs, not that each rule is correct in every case. The QVTo code is not
mutation-tested.

Checks across documents are stops, not diagnostics. A stop reports one
problem without its document location. Most such checks moved into
constraints; the remaining stops are a safety net. The cross-document
constraints still use \texttt{allInstances()}; moving them onto one root
object is decided but not implemented.

Queries are recomputed. QVTo caches mapping results but not queries, so
\texttt{edgeOf} or a \texttt{Surface} address is recomputed wherever used.
Several queries scan every \texttt{Process} in the cluster, so work grows
with the square of \texttt{Process} count. For much larger
clusters, hot queries would become mappings or precomputed properties.
Capacity needs to be measured first.

Capacity is checked per machine. A \texttt{Process} is eligible for a machine
that can hold it alone. The resolution does not sum what all
\texttt{Process}es request of one machine.

Two small modelling choices remain. When two \texttt{Process}es provide the
same \texttt{Surface}, the first in name order wins. The order between
\texttt{ReconcileUnit}s is per \texttt{Project}, not per \texttt{Application},
because Flux orders whole units.

Provenance digests differ by design. Input digests are hashes over each
implementation's own model form. Every digest reaching a generated file—the
\texttt{Revision}, an \texttt{Asset} name, the policy job name—is reproduced.

The \texttt{knowledge} example is not resolved. It models a \texttt{Project}
being retired. Its successor, \texttt{knowledge-platform}, is.

The Eclipse run configuration is not tested. The build uses the standalone
executor. The configuration and \texttt{plugin.xml} registration are only
run manually.

\subsection{Reflection}
\label{sec:reflection}

The most time-consuming part was the \texttt{Revision}. Writing the production
implementation's JSON form of an \texttt{Application} in OCL, one field at a
 time, took about one sixth of \texttt{resolution.qvto}. Every mistake showed
only as a different hash, but it was worth the effort. Once the \texttt{Revision}s
matched, they verified nearly every value of ten \texttt{Application}s at once,
which would have been impractical to check by hand.

QVTo was a good fit for the work. Most rules are queries over the whole
cluster, and OCL expresses these naturally. The explicit trace also made every
reference between created elements visible.

Three language details cost extra time. The keywords \texttt{resolve},
\texttt{from} and \texttt{access} prevented naming the black-box unit after its
Java package, so two metamodel features had to be written \texttt{\_from} and
\texttt{\_access}. A multi-statement \texttt{if} needs braces. Inside an object
expression, \texttt{result} refers to the enclosing mapping result, not the
object being created.

With hindsight, I would have planned the evidence with the examples from the
start. The expected model of \texttt{secrets} and the parity checks for
\texttt{knowledge-platform} were only added at the end when a review asked which
examples had no comparison. The Task~1 model of \texttt{minimal} should have been
kept unchanged beside the updated one, so the one independent oracle would
remain independent.
