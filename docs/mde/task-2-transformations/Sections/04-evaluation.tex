\section{Tests and Evaluation}
\label{sec:evaluation}

The transformations are tested by running them on eight examples and comparing
their output with oracle files. The oracles come from the production
implementation processing the same input documents, so matching them shows
both implementations derive the same values.

The build runs six test types on every change.

\begin{itemize}
  \item \textbf{Lowered models.} For the four examples with shared
    declarations, the lowered model is written as JSON and compared
    byte-for-byte with the expected Effective Intent.
  \item \textbf{Dependency edges.} For each example, the resolved edges are
    exported as JSON and compared byte-for-byte with the expected file. These
    tests read only files the pipeline wrote, so they check the pipeline as a
    user would run it.
  \item \textbf{Revisions.} Each expected resolved file records its
    \texttt{Revision}, a digest over the \texttt{Application} element as the
    production implementation writes it. Matching \texttt{Revision}s confirm
    that the same values were derived for that element
    (Section~\ref{sec:revisionevidence}). The digest covers the element's own
    decisions, not the whole resolved model: the path plan, the network
    policies and the Vault documents fall outside it, which is what the
    complete-model and generated-file comparisons below are for.
  \item \textbf{Complete expected models.} \texttt{minimal} and
    \texttt{secrets} have full expected \texttt{Resolved Deployment} models,
    compared using EMF's structural equality (\texttt{EcoreUtil.equals}),
    which checks every attribute and reference.
  \item \textbf{Generated files.} Since Task~3 templates decide nothing, every
    wrong value they write from a \texttt{Resolved Deployment} becomes a wrong
    byte in a generated file. Tests generate the files from the transformation
    output and compare each with the committed output.
  \item \textbf{Interface tests.} JUnit tests exercise the resolution with
    the smallest project that resolves, a project not in the input, and an
    \texttt{Asset} whose file is missing, which must stop the run with the
    file name. The estate pass is tested with one job planned over two
    projects, a job name that moves when a document changes, no job without
    documents, and two projects that carry different policy jobs. The lowering
    is tested with eight cases of merging shared declarations.
\end{itemize}

The Java code around the transformations must reach full line and branch
coverage and a 100% mutation score. These tools cannot measure QVTo, so the
QVTo code is verified only by the comparisons above.

\subsubsection{What the Revisions Show}
\label{sec:revisionevidence}

An \texttt{Application}'s \texttt{Revision} is the digest of its whole element
as the production implementation writes it: its \texttt{Process}es with image,
user, deadline, probes, placement, secrets, volumes, backups, environment and
edges; its \texttt{Exposure}s and routes; its \texttt{Release Gate} and
migration.

The transformation builds that text from its own \texttt{Resolved Deployment}
(Section~\ref{sec:blackbox}), so one different value, one extra environment
variable or one different order changes the digest. Ten \texttt{Application}s
across five examples have a \texttt{Revision} in an expected file, and all
ten match.

For these \texttt{Application}s, the \texttt{Revision} check verifies nearly
every value of each element at once, where a hand-written model would have to
check the fields one by one. A further test confirms the \texttt{Revision}
moves when a decision changes: raising the memory in \texttt{minimal} from 256Mi to
512Mi changes it, but changing the snapshot capture time, which decides
nothing, does not.

\subsubsection{What the Generated Files Show}
\label{sec:treeevidence}

The generated files carry the values no \texttt{Revision} covers. The
transformation output reproduces 167 committed files byte-for-byte, across
five examples and the cluster-wide tree, including the estate pass job.

\subsubsection{Where the Evidence Is Thin}
\label{sec:thin}

Two examples, \texttt{edge} and \texttt{observability}, have no
\texttt{Revision}, no committed tree and no expected model. Their edge files
contain no edges, so the evidence that they resolve correctly is that the run
succeeds and that other examples, which look up their proxies and collectors,
reproduce their expected files.

The \texttt{secrets} model is a reviewed output rather than an independent
oracle. It flags any later change in that output, and the review of it found
one gap in the specification: the Secret Store network policy admits nobody
inbound even though every holder of a Secret may send to it.

The hand-written model of \texttt{minimal} from Task~1 was updated after
hand-in to follow the metamodel changes of Appendix~\ref{app:target}. Its
\texttt{Revision} was taken from the production implementation, so one field
no longer checks independently.

\subsubsection{Defects Found by Testing}
\label{sec:defects}

Comparisons found a defect no single example had shown: the path plan
placed cluster-wide route files under \path{apps/edge/}, which is also the
directory of the project named \texttt{edge}. The \texttt{edge} example's files would
have mixed with routes from every other \texttt{Project}. The fix moved all
cluster-wide files under \path{estate/} in both implementations, and the
committed trees now hold each file at its correct path.

\subsection{Limitations}
\label{sec:limitations}

The oracles come from another implementation, so agreement shows two
implementations of the specification decide the same, not that the
specification itself is correct. Only the hand-written model of
\texttt{minimal} was written directly from the specification.

Eight examples form a sample, on which every rule runs and agrees. The
\texttt{knowledge} example, which models a \texttt{Project} being retired, is
not one of them; its successor \texttt{knowledge-platform} is.

Checks across documents that remain in the transformation are stops, and a
stop reports one problem without its location in the documents. Most such
checks moved into constraints. The cross-document constraints still use
\texttt{allInstances()}; moving them onto one root object is decided but
not implemented.

QVTo caches mapping results but not queries, so \texttt{edgeOf} or a
\texttt{Surface} address is recomputed wherever used. Several queries scan
every \texttt{Process} in the cluster, so work grows with the square of
\texttt{Process} count; for much larger clusters, hot queries would become
mappings or precomputed properties, and capacity needs to be measured first.

A \texttt{Process} is eligible for a machine that can hold it alone; the
resolution does not sum what all \texttt{Process}es request of one machine.

When two \texttt{Process}es provide the same \texttt{Surface}, the first in
name order wins. The order between \texttt{ReconcileUnit}s is set per
\texttt{Project}, not per \texttt{Application}, because Flux orders whole
units.

Each implementation hashes its own model form of the inputs, so their
provenance digests differ. Every digest that reaches a generated file (the
\texttt{Revision}, an \texttt{Asset} name and the policy job name) is
reproduced.

The Eclipse run configuration is not tested: the build uses the standalone
executor, and the configuration and \texttt{plugin.xml} registration are only
run manually.

\subsection{Reflection}
\label{sec:reflection}

The \texttt{Revision} took the most time. The OCL that writes the production
implementation's JSON form of an \texttt{Application}, one field at a time,
fills about one sixth of \texttt{resolution.qvto}, and every mistake in it
showed only as a different hash.

Most rules are queries over the whole cluster, which OCL states directly, and
the explicit trace made every reference between created elements visible, so
QVTo suited the work. In return, QVTo recomputes those queries wherever they
are used (Section~\ref{sec:limitations}).

The keywords \texttt{resolve}, \texttt{from} and \texttt{access} each
cost time, as did two rules of the language. \texttt{resolve} prevented naming
the black-box unit after its Java package, and \texttt{from} and
\texttt{access} forced two metamodel features
to be written \texttt{\_from} and \texttt{\_access}. A multi-statement
\texttt{if} needs braces. Inside an object expression, \texttt{result} refers
to the enclosing mapping result, not the object being created.

With hindsight, the evidence should have been planned with the examples
from the start. The expected model of \texttt{secrets} and the parity checks
for \texttt{knowledge-platform} were only added at the end, when the examples
without a comparison were identified. The Task~1 model of \texttt{minimal}
should have been kept unchanged beside the updated one, so the one
independent oracle would remain independent.
