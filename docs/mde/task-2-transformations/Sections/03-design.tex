\section{Solution Design}
\label{sec:design}

Task~2 uses three QVT-Operational transformations of varying sizes. The flattening
(\texttt{lower.qvto}) is 340 lines with 37 mapping operations and 8
queries. The resolution (\texttt{resolution.qvto}), the main transformation, is the largest, about 1700
lines, roughly five times the flattening, with 8 mapping operations and 140 queries. The final pass
(\texttt{estate.qvto}) is the smallest, about 130 lines, with no mappings but one helper.

Figure~\ref{fig:pattern} shows the metamodels each transformation reads and
writes. The three transformations differ in kind, and all are one-way.

\begin{itemize}
  \item The flattening is endogenous and horizontal: it reads and writes the source
    metamodel at the same abstraction level, producing a new model. One \texttt{Project}
    goes in, one comes out.
  \item The resolution is exogenous and vertical, a refinement: it reads source
    and pinned-input metamodels and writes the target metamodel, taking several
    input models and producing one output.
  \item The final pass is endogenous and in-place: it updates the resolved models
    of a run through an \texttt{inout} extent.
\end{itemize}

\subsection{The Flattening}
\label{sec:flattening}

The flattening, \texttt{lower.qvto}, maps each authored \texttt{Project} onto an
\texttt{EffectiveProject}. Every \texttt{Process} carries all shared declarations that apply to
it, while the \texttt{Project} and \texttt{Application} carry none. Task~2 extended the Task~1
implementation with API access and engine \texttt{Grant}s (declared access to a secret of a database or transit engine).

Its 37 mappings are nearly all simple copies of declarations from parent to child. Its queries perform the merging logic. A
list such as \texttt{secrets}, dependency edges, configuration files, or environment entries becomes
the union of declarations from \texttt{Project}, \texttt{Application}, and
\texttt{Process} levels. If several levels declare the same item, the most
specific declaration wins. A single value, such as the startup budget or cutover, also comes from the most specific level that declares it. Cutover determines whether the \texttt{Application} keeps serving during an update. Memory and CPU remain
only on the \texttt{Process}.

A shared declaration needs a separate copy in each receiving
\texttt{Process}. Reusing a cached mapping result would move that object
to the last \texttt{Process}, because an EMF object can have only one
container. Inside \texttt{Process::lower}, \texttt{self} is the receiving
source \texttt{Process}. Passing it to each declaration's
\texttt{copyFor(self)} makes the cache distinguish the required copies.
For migrations, a disjuncts mapping dispatches to the copy operation for
the source subtype: managed, self-managed or no migration. The caller can
copy any migration without repeating that subtype selection.

The flattening has no aborts of its own: it only copies and merges declarations
after input checks. Missing values needed for deployment, such as an
unlocked image, are rejected later by the resolution.

\subsection{Interface, Mappings and Queries}
\label{sec:shape}

Example~\ref{lst:header} shows how the inputs are grouped: \texttt{intent}
contains the deployment declarations, \texttt{pinned} contains their
supporting inputs, and \texttt{resolved} receives the target model.

\begin{lstlisting}[language=qvto, style=report, caption={The Signature and Inputs of the Resolution, Abridged}, label={lst:header}]
transformation resolution(in intent : PI, in pinned : IN, out resolved : RD)
	access library Hashing;
configuration property project : String;    -- the project this run resolves
property projects : Sequence(EffectiveProject) =
	intent.rootObjects()[EffectiveProject]->sortedBy(p | p.project)->asSequence();
property lock : ImagesLock = pinned.rootObjects()[ImagesLock]->any(true);
-- and likewise contract, snapshot, proofs and assetFiles
main() {
	projects->select(p | p.project = project)->any(true).map deployment();
}
\end{lstlisting}

The intent extent holds, for every \texttt{Project} in the run, its authored model and
its \texttt{EffectiveProject}, plus the \texttt{Platform Intent}. Authored models are kept only
because \texttt{Platform Intent} references them via Ecore cross-references. Every rule
reads the \texttt{EffectiveProject} models.

The pinned extent holds the node contract, images lock, cluster-state
snapshot, and each \texttt{Project}'s migration proof (the schema version its
migration was tested against), and one \texttt{AssetFile} per configuration file. Two configuration
properties supply the \texttt{Project} name to resolve and the schema-package digest (hash of the metamodel version) to include in the provenance record.

Properties such as \texttt{projects} and \texttt{lock} select these inputs
once. Another selects the \texttt{Platform Intent}. A dependency lookup navigates through
\texttt{projects.applications.processes}, so it searches only the
flattened models supplied to this run. Sorting \texttt{Project}s by name
makes the result independent of input file loading order.

Mappings are used for objects that other rules must reference. For example,
the trace connects a source \texttt{Process} to its
\texttt{ResolvedProcess}, allowing a route to reuse that result through
\texttt{resolveone}. A probe belongs only to its parent and needs no such
lookup, so a query creates it with an object expression instead. Each
mapped target type has one mapping, making the source and result type
sufficient to identify the trace entry. Callers filter elements with
\texttt{->select} before invoking a mapping. No mapping uses a
\texttt{when} guard or inherits from another.

Queries calculate values without modifying the input models. They return
scalars such as deadlines, new contained objects such as backup plans, or
the target spelling of an enumeration value, for example
\texttt{businessHours} as \texttt{business-hours}. The calling mapping
assigns the result. Abort queries terminate the run when a value cannot be
derived (Section~\ref{sec:aborts}). The final pass uses a helper instead
because it adds files to an existing output model.

Mappings run in a fixed order. The deployment mapping creates the
\texttt{Project}'s \texttt{ReconcileUnit} and local references to prerequisite
units first, then \texttt{Application}s, provenance, and the path plan (the step
that gives every generated file its path). Each \texttt{Application} maps
its \texttt{Process}es before its \texttt{Exposure}s, \texttt{ReleaseGate}, and migration, because those
refer to \texttt{Process}es through the trace.

\subsubsection{The Process Mapping}
\label{sec:processrule}

Example~\ref{lst:process} shows how the \texttt{Process} mapping combines
these rules. The image lock entry supplies the repository and digest,
\texttt{deadlineOf} supplies the deadline, and \texttt{eligible} filters the
nodes. Optional fields are assigned only where they apply. For example, a
one-off job has no switchover: assigning the enumeration's default value
would incorrectly record a blue/green deployment strategy for that job.

\begin{lstlisting}[language=qvto, style=report, caption={The Process Mapping, Abridged}, label={lst:process}]
mapping PI::Process::process(in app : EffectiveApplication, in prj : EffectiveProject)
		: ResolvedProcess {
	init { var own : LockedImage := locked(self.image); }
	name := self.name;
	image := own.repository + '@' + own.digest;
	if self.lifecycle = Lifecycle::application
		then switchover := switchoverOf(app, self) endif;
	deadline := inSeconds(deadlineOf(self));
	secrets := self.secrets->collect(g | g.resolvedFor(self));
	placement := object ResolvedPlacement {
		eligibleNodes := contract.nodes->select(n | eligible(self, n))->collect(n | n.name);
	};
	dependencies := self.dependsOn->collect(e | edgeOf(e));
	environment := environmentOf(self, prj)->sortedBy(e | e.name);
}
\end{lstlisting}

\subsubsection{The Edge Rule}
\label{sec:edgerule}

A dependency edge names an \texttt{Application} and a \texttt{Surface}
(named port). For example, an edge to \texttt{platform-postgres} names its
\texttt{postgres} port. The query
\texttt{edgeOf} finds the first \texttt{Process} in the cluster belonging to
that \texttt{Application} that provides that \texttt{Surface}. The resolved edge
records the \texttt{Process} address and the network peer the consumer may
reach. If no \texttt{Process} provides the \texttt{Surface}, the
\texttt{Platform Intent} external provider list is tried as a fallback. This mechanism allows the \texttt{auth} \texttt{Project} to reach a mail server outside the cluster. If neither has it,
the run aborts.

During migration to this deployment system, the \texttt{Platform Intent}'s
\texttt{HandoverLedger} records where applications still served by the
previous system run. Their resolved addresses and peers use the recorded
namespace and workload name until they move.

\subsubsection{Environment Variables and Placeholders}
\label{sec:placeholders}

A \texttt{Process}'s environment files consist of a base file and, optionally,
one overlay per cluster. The resolution selects the overlay named by the
\texttt{Platform Intent}'s cluster, then replaces base entries with overlay
entries of the same name. Other base entries remain.

An entry may contain a placeholder, such as
\texttt{DB\_HOST=\$\{dependency:platform-postgres.host\}}. The query
\texttt{Placeholder::entryFor} handles four kinds. A secret placeholder becomes a
reference to a key of a secret the \texttt{Process} holds, so the value never
appears in a file. A dependency placeholder takes the host or port of the
\texttt{Process} dependency edge from \texttt{edgeOf}. An exposure placeholder takes
the URL, host or scheme of an \texttt{Exposure} anywhere in the cluster. An identity
placeholder takes the \texttt{Process} name, namespace or Vault role (the
binding that grants its service account a secret-access policy). Text after a placeholder is kept, as in
\texttt{AUTH\_LOGIN\_URL=\$\{exposure:auth.public\#url\}/login}.

The runtime profile then adds the platform-defined variables for the
selected language runtime, such as \texttt{PORT}. Declaring one of these
names in an environment file aborts the run, because it would conflict with
the platform-defined value.

\subsubsection{Network Peers}
\label{sec:peers}

The ingress policy of a \texttt{Process} combines peers from six sources
(Table~\ref{tab:rules}). Most require looking across \texttt{Project}s:
consumers with a dependency edge to the \texttt{Process}, migrations that
access its database, proxies, and the metrics collector named by the
\texttt{Platform Intent}. Each source yields tuples of rule, namespace,
\texttt{Process}, and port. Distinct \texttt{PolicyPeer} objects are not considered equal even if their field values match, because they are separate model elements. The union therefore uses
tuples and \texttt{asOrderedSet()} to remove duplicates before creating
\texttt{PolicyPeer} objects. The rule name remains part of each tuple, so
two rules allowing the same connection retain both rule identifiers.

\subsubsection{The Path Plan}
\label{sec:pathplan}

The path plan represents each generated file as an instance of a
\texttt{Deliverable} subclass, recording its path and the model elements
used to generate it. Each \texttt{Project} gets a namespace file, index and
default-deny network policy. If an \texttt{Application} synchronises secrets,
a \texttt{VaultConnection} file tells the secret operator which Vault
address to read.

Each \texttt{Application} gets a directory with one file per resource kind:
\begin{itemize}
  \item a workload file;
  \item a service account;
  \item RBAC;
  \item volume claims;
  \item a configuration map carrying \texttt{ReleaseGate} inputs as JSON;
  \item backups;
  \item a migration;
  \item a monitor;
  \item synced secrets;
  \item a network-policy file with one policy per \texttt{Process};
\end{itemize} Blue/green \texttt{Process}es add a \texttt{Canary} file.
Others add a \texttt{Service} file. Multi-replica \texttt{Process}es add a
disruption budget. Empty files are not planned, as they would generate unnecessary Kubernetes resources.

Each index lists the files Flux should apply from its directory. Network
policies are included in the generated output for review, but excluded from
these indexes while the specification's policy stage is render-only. This
allows their proposed connections to be inspected before enforcement. Each
\texttt{Exposure} gets a route file under its entry point (Traefik listener). Each service account
holding a secret gets a Vault policy and role.

Paths can therefore be inspected and compared before rendering. The
transformation has no separate path-collision abort. Templates receive
these paths rather than choosing them.

\subsection{The Trace and End Sections}
\label{sec:trace}

Gate members, routes, metrics scrapes (monitoring configurations), and per-\texttt{Process} files all refer
to a \texttt{ResolvedProcess}. They find it by calling
\texttt{p.resolveone(ResolvedProcess)} on the source \texttt{Process},
which the \texttt{Application} mapping has already transformed
(Section~\ref{sec:shape}).

The \texttt{end} sections set values whose prerequisites are created by the
mapping body. The \texttt{Revision} must wait until the
\texttt{Application} is complete. The migration job tag then takes a prefix
of that digest so both identify the same release. Similarly, the render
hash is computed after all input digests have been recorded, and
\texttt{ReconcileUnit} dependencies are assigned after their local
reference objects exist. Each output contains its own unit and name-only
\texttt{ReconcileUnit} objects for prerequisite units in other projects;
\texttt{after} points to those local objects, not into another output model.

\subsection{The Black-Box Library}
\label{sec:blackbox}

A digest is a SHA-256 hash over canonical text. OCL lacks a byte-hashing
operation, so the Java class \texttt{Hashing} provides three operations that can be called from OCL expressions. \texttt{digestOf} walks any model element reflectively, writes
canonical JSON and hashes it for input provenance. \texttt{textDigestOf} hashes a file's text, for the
content-derived names of configuration files. \texttt{rawDigestOf} hashes a string as-is.

The \texttt{Revision} uses \texttt{rawDigestOf} to hash the canonical JSON representation directly. Generated files carry this
digest, so it must match the oracle exactly. The specification hashes the
\texttt{Application} configuration in canonical JSON (RFC~8785). That
specified JSON has a different structure from the Ecore target model. The OCL query
\texttt{elementJson} therefore constructs the required JSON from the source
and target models, sorting keys, omitting absent values and using the
specified representation of each value. The black box only hashes this
text. The transformation determines which values it contains.

Calls explicitly cast model elements to \texttt{EObject} before invoking
the library's contextual operations. The standalone runner and Eclipse plug-in both register the \texttt{Hashing}
library, and the QVTo modules access it by import.

\subsection{The Final Pass}
\label{sec:finalpass}

One job installs the Vault policies and roles from every \texttt{Project}
into the Secret Store. Its name contains a digest of all these documents.
Changing a document therefore gives the next deployment a new job name,
causing the updated configuration to be installed.

The final pass, \texttt{estate(inout rendered : RD)}, runs once over all
\texttt{Resolved Deployment}s produced together. It collects every
\texttt{VaultPolicyFile} and \texttt{VaultRoleFile}, writes each as
canonical JSON in OCL, sorts them by file name, hashes the whole with
\texttt{rawDigestOf}, and plans the job, configuration map, service account
and network policy. These files and their index are stored in the first
model in the caller's project list, so the job is generated once for the combined output.

The pass also plans one cluster-wide route forwarding Flux events to the
Reporter.
All resolutions normally share one \texttt{Platform Intent}. A defensive
assertion rejects different job namespaces or images if the pass is called
directly with models from different runs. It does not compare every job setting.

\subsection{Aborts and Running the Transformations}
\label{sec:aborts}

Fifteen fatal assertions in the resolution abort the run when a value cannot
be derived. Thirteen are in abort queries that a rule calls instead of
returning an invalid value. For example, \texttt{locked} returns the lock
entry for an image or calls \texttt{unlocked}, whose assert fatal ends the
run with \texttt{E\_UNLOCKED\_IMAGE}. Two check \texttt{ReleaseGate}
preconditions at the start of the gate mapping. The final pass has one
more, for the inconsistent job namespaces or images described above.

The checks reject missing inputs and providers, unsupported quantities,
unresolved placeholders, invalid secret references and author-defined
runtime-profile variables. They also reject backups without schedules or
engines, migrations without a database, blue/green deployments without
readiness or delivery services, and \texttt{Grant}s without a Secret Store.

Where the specification defines an error code, the message contains it. An
audience unsupported by any entry point needs no abort here: the
\texttt{E\_NO\_TIER\_FOR\_AUDIENCE} constraint already rejects it before
the transformation runs.

Three Java classes (\texttt{Lowering}, \texttt{Resolution}, and
\texttt{Estate}) run the transformations through QVTo's own
\texttt{TransformationExecutor}. They register the black box, set
configuration properties, pass the extents, and return the result or fail
with the executor's diagnostic. \texttt{Lowering} is the implementation name
of the flattening runner. The flattening does not change the abstraction level.

The build executes the transformations with QVTo's standalone executor on
every code change. The archive's \path{README.md} gives terminal and Eclipse
instructions for all three passes. It also maps each example to its output
project and explains the generated model extents.
