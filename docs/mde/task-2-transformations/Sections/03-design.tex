\section{Solution Design}
\label{sec:design}

The resolution consists of three QVT-Operational transformations. The lowering
(\texttt{lower.qvto}) is about 340 lines with 37 mapping operations and 3 helpers.
The main resolution (\texttt{resolution.qvto}) is about 1700 lines with 8 mapping
operations and 140 queries. The estate pass (\texttt{estate.qvto}) is about 130
lines with no mappings but one helper.

Figure~\ref{fig:pattern} shows the metamodels each transformation reads and writes.
The three differ in kind, each chosen for its job, and all are one-way.

\begin{itemize}
  \item The lowering is endogenous and horizontal: it reads and writes the source
    metamodel at the same abstraction level, producing a new model. One project
    goes in, one comes out.
  \item The resolution is exogenous and vertical, a refinement: it reads source
    and pinned-input metamodels and writes the target metamodel, taking N input
    models and producing 1 output.
  \item The estate pass is endogenous and in-place: it updates the resolved models
    of a run through an \texttt{inout} extent (M to N).
\end{itemize}

\subsection{The Lowering}
\label{sec:lowering}

The lowering, \texttt{lower.qvto}, turns each authored Project into an
EffectiveProject. Every Process carries all shared declarations that apply to
it, while the Project and Application carry none. Task~2 extended the Task~1
implementation with API access and engine grants.

It contains 37 small mappings, nearly all simple copies, plus three merge rules.
A list such as secrets, dependency edges, Assets or environment entries becomes
the union of declarations from Project, Application and Process levels. The
lowest level that declares an item wins. A single value such as startup budget
or cutover comes from the lowest level that declares it. Memory and CPU remain
only on the Process.

Two QVTo-specific details matter. A mapping returns its cached result when
called again on the same source, which would incorrectly share a single object
among multiple processes. To prevent this, every shared copy uses a mapping with
the Process as a parameter (\texttt{copyFor(self)}), which keys the trace on the
source-process pair. A migration is one of three subclasses, so its copy uses
a disjuncts mapping that selects the subclass at runtime.

The lowering has no stops. The OCL constraints run before it, so every input
it sees is valid.

\subsection{Interface}
\label{sec:interface}

Example~\ref{lst:header} shows the resolution's signature. It reads two extents
from two metamodels and writes one extent of a third.

\begin{lstlisting}[language=qvto, style=report, caption={The Signature and Inputs of the Resolution, Abridged}, label={lst:header}]
transformation resolution(in intent : PI, in pinned : IN, out resolved : RD)
	access library Hashing;
configuration property project : String;    -- the project this run resolves
property estate : Platform = intent.rootObjects()[Platform]->any(true);
property projects : Sequence(EffectiveProject) =
	intent.rootObjects()[EffectiveProject]->sortedBy(p | p.project)->asSequence();
property lock : ImagesLock = pinned.rootObjects()[ImagesLock]->any(true);
-- and likewise contract, snapshot, proofs and assetFiles
main() {
	projects->select(p | p.project = project)->any(true).map deployment();
}
\end{lstlisting}

The intent extent holds, for every project in the run, its authored model and
its EffectiveProject, plus the Platform Intent. Authored models remain only
because Platform Intent references them via Ecore cross-references. Every rule
reads the EffectiveProject models.

The pinned extent holds the node contract, images lock, snapshot, each project's
migration proof, and one AssetFile per configuration file. Two configuration
properties provide non-derived inputs: the project name to resolve, and the
schema package digest for provenance recording.

The seven properties select each input once by type from the root objects of
its extent. This is the only way the transformation accesses other documents.
Every rule navigates from one of these properties; no rule calls
\texttt{allInstances()}.

A query over every Process in the cluster uses
\texttt{projects.applications.processes}, whose extent is exactly the run's
documents. Projects are sorted by name so that the first provider of a service
is consistent across runs and implementations.

\subsection{Mappings and Queries}
\label{sec:shape}

QVTo provides two ways to create target objects. A mapping operation records
its source and result in the trace. Other rules find that result later using
\texttt{resolveone}. Calling the same mapping twice on the same source returns
the cached result. An object expression inside a query creates an object that
no other rule needs to locate.

The transformation uses a mapping exactly where another rule must reference
the result. Each target type has exactly one mapping, so the type alone identifies
the result: \texttt{p.resolveone(ResolvedProcess)} needs no
\texttt{resolveIn}. No mapping uses a \texttt{when} guard or inherits from
another; the caller selects what to map using \texttt{->select}, keeping the
choice visible in one place.

Queries are side-effect free. Many attach to model types, such as
\texttt{Grant::resolvedFor}. They serve four purposes.

A value query derives a single value, such as a deadline or an address. An object
query builds a contained object, such as a probe or a backup plan. A spelling
query turns a source enumeration literal into the string the target records, for
example \texttt{AlertClass::businessHours} into \texttt{business-hours}. Stop
queries such as \texttt{unlocked} raise a fatal assertion instead of returning a
value (Section~\ref{sec:stops}).

The estate pass contains the sole QVTo helper, an operation with side effects
that adds files to a model it updates in place.

Mappings run in a fixed order. The deployment mapping creates ReconcileUnits
first, then Applications, provenance and the path plan. Each Application maps
its Processes before its Exposures, ReleaseGate and migration, because those
refer to Processes through the trace.

\subsubsection{A Process}
\label{sec:processrule}

Example~\ref{lst:process} shows the start of the Process mapping. The init
section looks up the lock entry once, so assignments reuse it. Each assignment
calls a query from Table~\ref{tab:rules}. An optional feature is assigned
only when its condition holds: assigning an unset value would mark the feature
as set, making the model state a value nothing derived.

\begin{lstlisting}[language=qvto, style=report, caption={The Process Mapping, Abridged}, label={lst:process}]
mapping PI::Process::process(in app : EffectiveApplication, in prj : EffectiveProject)
		: ResolvedProcess {
	init { var own : LockedImage := locked(self.image); }
	name := self.name;
	image := own.repository + '@' + own.digest;
	if self.lifecycle = Lifecycle::application
		then switchover := switchoverOf(app, self) endif;
	deadline := inSeconds(deadlineOf(self));
	secrets := self.secrets->collect(g | g.resolvedFor(self));
	placement := object ResolvedPlacement {
		eligibleNodes := contract.nodes->select(n | eligible(self, n))->collect(n | n.name);
	};
	dependencies := self.dependsOn->collect(e | edgeOf(e));
	environment := environmentOf(self, prj)->sortedBy(e | e.name);
}
\end{lstlisting}

\subsubsection{A Dependency Edge}
\label{sec:edgerule}

A dependency edge names an Application and one of its Surfaces, for example
platform-postgres and postgres. The query edgeOf finds the first Process in
the cluster belonging to that Application that provides that Surface. The
resolved edge records the Process address and the network peer the consumer
may reach. If no Process provides the Surface, the Platform Intent's external
provider list is tried; this is how auth reaches a mail server outside the
cluster. If neither has it, the run stops.

While a Project still runs at its old location, as the handover ledger records,
its address and peer use that location's namespace and name, so a consumer
can depend on it before it moves.

\subsubsection{Environment Variables and Placeholders}
\label{sec:placeholders}

A Process env files consist of a base file and, optionally, one overlay per
cluster. The resolution keeps base entries not replaced by the overlay for the
Platform Intent's cluster.

An entry may contain a placeholder, such as
\texttt{DB\_HOST=\$\{dependency:platform-postgres.host\}}. The query
Placeholder::entryFor handles four kinds. A secret placeholder becomes a
reference to a key of a secret the Process holds, so the value never appears
in a file. A dependency placeholder takes the host or port of the Process
edge from edgeOf. An exposure placeholder takes the URL, host or scheme of
an Exposure anywhere in the cluster. An identity placeholder takes the Process
name, namespace or Vault role. Text after a placeholder is kept, as in
\texttt{AUTH\_LOGIN\_URL=\$\{exposure:auth.public\#url\}/login}.

The runtime profile then adds its own variables. An author who writes one of
them in an env file stops the run, because one name would have two values.

\subsubsection{Network Peers}
\label{sec:peers}

The ingress of a Process is a union of six sources (Table~\ref{tab:rules}).
Most look at other Projects: consumers whose edges name it, migrations of
Applications whose database it holds, proxies and metrics collector that the
platform names. Each source yields tuples of rule, namespace, Process and port.
The union uses asOrderedSet() before tuples become PolicyPeer objects. Building
plain tuples first matters: two objects are never equal in OCL, so a union of
objects would incorrectly keep a peer admitted twice.

\subsubsection{The Path Plan}
\label{sec:pathplan}

The path plan assigns each generated file its path as a Deliverable subclass
that refers to the elements it generates from. The Project gets a namespace file,
index, default-deny network policy, and the secret operator connection where
an Application syncs secrets.

Each Application gets a directory with one file per resource kind: workloads,
Canaries for blue/green Processes, Services for others, service accounts, RBAC,
volume claims, configuration map (carrying ReleaseGate inputs as JSON), backups,
disruption budgets for multi-replica Processes, migration, monitor, synced
secrets, and a network-policy file with one policy per Process. Empty files are
not planned.

Each index lists the files of its directory that Flux applies. Network
policies are generated but not yet applied, so no index lists them. Each Exposure
gets a route file under its entry point. Each identity holding a secret gets a
Vault policy and role.

Because paths are in the model, two files claiming one path can be detected
before any text is written, and Task~3 templates decide no path.

\subsection{The Trace and Late Assignment}
\label{sec:trace}

Every reference from one created element to another goes through the trace. A
ReleaseGate member, route, scrape and every per-Process file refer to a
ResolvedProcess, found with p.resolveone(ResolvedProcess) on the source
Process. This works because the Application mapping maps its Processes first.

Four values can only be computed once the rest of the model exists. They use
end sections, which run after the mapping body finishes.

The Application revision, a digest of its complete element, names the release
and appears in every generated Canary. The migration file tag uses the first
digits of that revision. The provenance render hash covers every input digest.
The order between ReconcileUnits refers to units created by the same mapping.

\subsection{The Black-Box Library}
\label{sec:blackbox}

A digest is a SHA-256 hash over canonical text. OCL lacks a byte-hashing
operation, so the Java class Hashing provides three contextual operations:
digestOf walks any model element reflectively, writes canonical JSON and hashes
it; textDigestOf hashes a file's text as the production implementation does;
rawDigestOf hashes a string as-is.

The revision uses the third. Generated files carry it, so it must equal the
production implementation's revision, which is the digest of the Application
element in that implementation's JSON form, a shape the target metamodel does
not have. The query elementJson therefore writes that element as text in OCL,
from source and target model together: keys sorted, absent values omitted, every
value spelled as the production implementation spells it. The black box only
hashes the result. This keeps every decision about what the revision covers
inside the transformation, making the revision a strong test
(Section~\ref{sec:results}).

Two QVTo implementation details shaped the library. An operation taking a
plain EObject is not found on a model element, because a model type does not
conform to EObject in the compiler, so each call casts first:
p.oclAsType(ECORE::EObject).digestOf(). The unit cannot be named after the
Java package because resolve is a QVTo keyword, so it registers as
dev.jorisjonkers.deploykit.emf.hashing, by the runner outside Eclipse and
by plugin.xml inside.

\subsection{The Estate Pass}
\label{sec:estatepass}

One generated job writes every Project's Vault documents into the secret store.
Its name is a digest over all of them, so changing any document starts a new
job. No single resolution can compute that name.

The estate pass, estate(inout rendered : RD), runs once over all Resolved
Deployments produced together. It collects every VaultPolicyFile and VaultRoleFile,
writes each as canonical JSON in OCL, sorts them by file name, hashes the
whole with rawDigestOf, and adds the job's four files and their index to the
first model. It also adds the route for the delivery tool's events to the
platform's reporter, which likewise belongs to no Project. It stops if two
models carry different jobs, because one run has one Platform Intent.

Its source and target are the same metamodel and it changes models in place,
which QVTo expresses with an inout extent.

\subsection{Stops}
\label{sec:stops}

Fifteen fatal assertions in the resolution and one in the estate pass stop the
run when a value cannot be derived. Thirteen are in stop queries that a rule
calls instead of returning an invalid value. For example, locked returns the
lock entry for an image or calls unlocked, whose assert fatal ends the run
with \texttt{E\_UNLOCKED\_IMAGE}. Two check ReleaseGate preconditions at the start of
the gate mapping. The estate pass one stops when two Projects carry different
policy jobs.

The stops cover: an image missing from the lock; an edge no Process or
provider serves; a placeholder naming nothing or a secret the Process does not
hold; a runtime-profile variable written by an author; an Asset whose file is
missing or contains a placeholder; a backed-up Volume without schedule or
database engine; a migration reaching no database; a blue/green Application
without readiness, ReleaseGate or delivery policy; a Grant without a secret
store; and a quantity in a unit the model does not read.

Where the specification defines an error code, the message contains it. An
audience that no entry point carries has no stop because a constraint
\texttt{E\_NO\_TIER\_FOR\_AUDIENCE} already refuses it before the run.

\subsection{Running the Transformations}
\label{sec:running}

Three Java classes, Lowering, Resolution and Estate, run the transformations
through QVTo's TransformationExecutor. They register the black box, set
configuration properties, pass the extents, and return the result or fail with
the executor's diagnostic.

The pipeline builds the extents from parsed and checked documents and writes
every example's models under target/parity/<example>/. Appendix~\ref{app:running}
gives the steps.
