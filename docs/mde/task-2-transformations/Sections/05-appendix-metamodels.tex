\section{Changes to the Task 1 Metamodels}
\label{app:metamodels}

This appendix lists the changes between the Task~1 metamodels and those the
Task~2 transformations read and write. The comparison was done by comparing
class by class and feature by feature in each .ecore file.

Four kinds of change exist. A third metamodel for the pinned input set
(Appendix~\ref{app:pinned}). The target metamodel gained derived values and twelve
kinds of generated file (Appendix~\ref{app:target}). The source metamodel gained
declarations the other examples need (Appendix~\ref{app:source}). Four grammars
(Appendix~\ref{app:grammars}).

No class was removed. The Task~1 hand-in showed OCL helper definitions such as
levelsAbove and derivesDatabase as derived attributes in the diagram. They
remain OCL definitions in project-intent.ocl and were never Ecore features.

\subsection{The Pinned Inputs Metamodel}
\label{app:pinned}

The pinnedinputs package holds the documents the resolution reads beside the
source models. Task~1 decided only authored documents get a metamodel. These
documents are not authored by a Project owner, and the resolution needs them as
models, so they form a separate package instead of joining the source metamodel.

The node contract is generated from the platform team's machine descriptions.
Another Process publishes the images lock and the snapshot. A Project's build
writes its migration proof.

The source metamodel structure is compared with the production implementation
schemas through a committed descriptor. Adding these classes would list documents
those schemas do not hold. No target metamodel class refers to them: the
Resolved Deployment records the values read from them, and their digests.

Two attributes are plain strings, an exception to Task~1's rule of
enumerations over free-form strings. A Node's disk medium is not the source
metamodel's Media enumeration because the node contract lists media no Process
may request, such as sdcard. The resolution compares the spelling instead, and
does the same for architecture. The values come from generated documents, not
from an author, so the risk of author typo does not apply.

\subsection{Changes to the Target Metamodel}
\label{app:target}

The target metamodel has two halves: the decisions the Platform Intent takes,
and the generated-file entries of the path plan. Both grew.

The root class is unchanged, but what one instance holds changed. Task~1 planned
one Resolved Deployment for the whole cluster. There is now one per Project
(Section~\ref{sec:perproject}). A ResolvedApplication inside is still the
projection one repository publishes.

\paragraph{Decisions.} Figure~\ref{fig:targetdecisions} shows every decision
class that is new or changed. Table~\ref{tab:targetvalues} gives the reason for
each.

Task~1 named many decisions in prose but gave classes only to what its worked
example needed. The other examples also need migrations, backups that connect to
their database, Secrets that reach the cluster, API access, Sidecars,
configuration files, and two cluster-wide values: the Vault policy job and
the route of the delivery tool's events.

\paragraph{Generated Files.} Figure~\ref{fig:targetfiles} shows every
subclass of Deliverable. Task~1 had nine. There are now 21. Three kinds of
change were made.

One file per Application: workload, Canary and identity files, which Task~1
tied to one Process, now list processes because the specification writes one
file per Application holding all its Process resources. Task~1's worked example had
one Process, so this difference did not show. For the same reason, the network
policy file holds one ProcessPolicy per Process, and the Secret file refers
to its Application and holds one SecretHolder per identity, since a Backup identity
holds Secrets too.

Monitors: MonitorFile gained timeout and kind. A blue/green Process is scraped
through its Pods; any other through its Service.

Twelve new file kinds: Services, volume claims, configuration maps, backups,
disruption budgets, migrations, RBAC, the secret operator connection, Vault
policies and roles, the policy job and the events route.

\subsection{Grammars for the Pinned Inputs}
\label{app:grammars}

The pinned inputs use grammars rather than a Java YAML reader or hand-written
XMI, so both implementations read the same YAML files and their results can
be compared.

Four grammars were added beside the Project and Platform grammars:
NodeContract, ImagesLock, ClusterState and MigrationProof. Each inherits
the Project grammar, reusing its terminals, indentation tokens and scalar rule,
and adds only the rules for its own document. As with the Platform Intent, the
file name selects the grammar: node-contract.yml, images.lock.yml,
cluster-state.yml and migration-proof.yml.

Example~\ref{lst:grammar} shows the smallest grammar.

One input file changed: the Project grammar scalar terminal cannot contain a
colon, so the snapshot's capture time is now quoted, as digests and URLs already
were. The production implementation reads the same value either way.

\begin{lstlisting}[style=report, caption={The Grammar of the Cluster-State Snapshot, Abridged}, label={lst:grammar}]
grammar dev.jorisjonkers.deploykit.emf.syntax.ClusterState
	with dev.jorisjonkers.deploykit.emf.syntax.ProjectIntent
import "https://jorisjonkers.dev/deploy-kit/pinned-inputs/1"

ClusterState returns ClusterState:
	(('apiVersion' ':' apiVersion=Text)
	& ('kind' ':' kind=Text)
	& ('schemaVersion' ':' schemaVersion=Text)
	& ('cluster' ':' cluster=Text)
	& ('capturedAt' ':' capturedAt=Text)
	& ('bindings' ':' BEGIN (DASH BEGIN bindings+=Binding END)* END)
	& ('placements' ':' BEGIN (DASH BEGIN placements+=CurrentPlacement END)* END)
	& ('backups' ':' BEGIN (DASH BEGIN backups+=RollbackBackup END)* END)?);

Binding returns Binding:
	(('claim' ':' claim=Text)
	& ('node' ':' node=Text));
\end{lstlisting}
