\section{Changes to the Task 1 Metamodels}
\label{app:metamodels}

This appendix lists the changes between the metamodels handed in for Task~1
and the metamodels the transformations of Task~2 read and write, found by
comparing the two versions of each \texttt{.ecore} file class by class and
feature by feature. There are four kinds:

\begin{itemize}
  \item a third metamodel, the pinned inputs (Appendix~\ref{app:pinned});
  \item the target metamodel gained the values the transformation derives and
    twelve kinds of generated file (Appendix~\ref{app:target});
  \item the source metamodel gained the declarations the other examples need
    (Appendix~\ref{app:source});
  \item four grammars (Appendix~\ref{app:grammars}).
\end{itemize}

No class was removed. The Task~1 hand-in also showed several OCL helper
definitions, such as \texttt{levelsAbove} and \texttt{derivesDatabase}, as
derived attributes in the diagram; they are still OCL definitions in
\texttt{project-intent.ocl} and were never Ecore features.

\subsection{The Pinned Inputs Metamodel}
\label{app:pinned}

The package \texttt{pinnedinputs} holds the documents the resolution reads
beside the source models. Task~1 decided that only authored documents get a
metamodel; these documents are not authored by a project's owner, and the
resolution cannot read them without one, so they get a separate package
instead of joining the source metamodel. The node contract is generated from
the platform team's description of the machines, another process publishes the
images lock and the snapshot, and a project's build writes its migration
proof. The source
metamodel's structure is also compared with the production implementation's
schemas through a committed descriptor, and adding these classes to it would
have listed documents those schemas do not hold. No class of the target
metamodel refers to them: the resolved model records the values the resolution
reads from them, and their digests. Figure~\ref{fig:pinned} shows the
metamodel, and Table~\ref{tab:pinned} says what reads each class.

Two attributes are plain strings, an exception to Task~1's rule of
enumerations over free-form strings. A node's disk medium is not the source
metamodel's \texttt{Media} enumeration, because the node contract lists media
that no process may request, such as \texttt{sdcard}. The resolution compares
the spelling instead, and does the same for a node's architecture. The values
come from a generated document, not from an author, so the risk the rule guards
against, an author's typo, does not arise.

\subsection{Changes to the Target Metamodel}
\label{app:target}

The target metamodel has two halves: the decisions the platform takes, and the
generated-file entries of the path plan. Both grew.

The root class is unchanged, but what one instance holds changed: Task~1
planned one \texttt{ResolvedDeployment} for the whole cluster, and there is now
one per project (Section~\ref{sec:perproject}). A \texttt{ResolvedApplication}
inside it is still the projection one repository publishes.

\paragraph{Decisions.} Figure~\ref{fig:targetdecisions} shows every decision
class that is new or changed, and Table~\ref{tab:targetvalues} gives the reason
for each change. Task~1 named many of these decisions in prose but gave classes
only to what its worked example needed. The other examples also need
migrations, backups that connect to their database, secrets that reach the
cluster, API access, sidecars, configuration files, and two cluster-wide values:
the Vault policy job and the route of the delivery tool's events.

\paragraph{Generated Files.} Figure~\ref{fig:targetfiles} shows every
subclass of \texttt{Deliverable}. Task~1 had nine; there are now 21. Three
kinds of change were made.

\begin{itemize}
  \item \textbf{One file per application.} The workload, Canary and identity
    files, which Task~1 tied to one process, now list \texttt{processes},
    because the specification writes one file per application holding the
    resources of all its processes; Task~1's worked example had one process,
    so the difference did not show. For the same reason the network policy
    file holds one \texttt{ProcessPolicy} per process, and the secret file
    refers to its application and holds one \texttt{SecretHolder} per identity,
    since a backup identity holds secrets too.
  \item \textbf{Monitors.} \texttt{MonitorFile} gained \texttt{timeout} and a
    \texttt{kind}: a blue/green process is scraped through its pods, any other
    through its service.
  \item \textbf{Twelve new kinds of file}: services, volume claims,
    configuration maps, backups, disruption budgets, migrations, RBAC, the
    secret operator's connection, Vault policies and roles, the policy job and
    the events route.
\end{itemize}

\subsection{Grammars for the Pinned Inputs}
\label{app:grammars}

The pinned inputs are read with grammars rather than a Java YAML reader or hand-written XMI, so that both implementations read the same YAML files and their results can be compared. Four grammars were added beside the project and platform grammars:
\texttt{NodeContract}, \texttt{ImagesLock}, \texttt{ClusterState} and
\texttt{MigrationProof}. Each inherits the project grammar, so it reuses its
terminals, its indentation tokens and its scalar rule, and adds only the rules
for its own document. As with the platform document, the file name selects the
grammar: \path{node-contract.yml}, \path{images.lock.yml},
\path{cluster-state.yml} and \path{migration-proof.yml}.
Example~\ref{lst:grammar} shows the smallest. One input file changed: the
project grammar's scalar terminal cannot contain a colon, so the snapshot's
capture time is now quoted, as digests and URLs already were. The production
implementation reads the same value either way.

\begin{lstlisting}[style=report, caption={The Grammar of the Cluster-State Snapshot, Abridged}, label={lst:grammar}]
grammar dev.jorisjonkers.deploykit.emf.syntax.ClusterState
	with dev.jorisjonkers.deploykit.emf.syntax.ProjectIntent
import "https://jorisjonkers.dev/deploy-kit/pinned-inputs/1"

ClusterState returns ClusterState:
	(('apiVersion' ':' apiVersion=Text)
	& ('kind' ':' kind=Text)
	& ('schemaVersion' ':' schemaVersion=Text)
	& ('cluster' ':' cluster=Text)
	& ('capturedAt' ':' capturedAt=Text)
	& ('bindings' ':' BEGIN (DASH BEGIN bindings+=Binding END)* END)
	& ('placements' ':' BEGIN (DASH BEGIN placements+=CurrentPlacement END)* END)
	& ('backups' ':' BEGIN (DASH BEGIN backups+=RollbackBackup END)* END)?);

Binding returns Binding:
	(('claim' ':' claim=Text)
	& ('node' ':' node=Text));
\end{lstlisting}
