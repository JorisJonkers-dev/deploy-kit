KubeOrch comes closest: it maps service links to addresses and ports.
However, it has no shared platform policy or pinned-input model from which
to derive placement, locked images, or backups, and no resolved intermediate
model to test. KubeDiagrams could inspect the Task~3 output, while a
KubeOrch-style editor could author \texttt{Project Intent} using the same
Ecore metamodel as the transformation.

\subsection{The Transformation Language}
\label{sec:language}

The assignment permits ATL or QVT-Operational (QVTo). QVTo was chosen over ATL because it allows a transformation to read its own output within the same operation. That reading is essential for computing a release identifier: a \texttt{Revision} must cover the completed \texttt{Application}, including the values derived for its \texttt{Process}es, routes, and \texttt{ReleaseGate}. ATL's target models are write-only, so this calculation would need to reconstruct the resolved values from the source or run a further transformation over the output.
QVTo lets the deployment mapping read the completed target model in its
\texttt{end} section. This keeps the release identifier with the operation
that constructs the deployment and gives it access to the values that
operation has produced.

The required construction order also favoured QVTo. Resolved
\texttt{Process}es must exist before routes and \texttt{ReleaseGate}
members can refer to them. The \texttt{Revision} must be computed after
these objects have been populated. Explicit mapping calls make those
prerequisites visible in the caller, with trace lookup supplying the
references to previously created objects. ATL's called rules could also
express an execution order. The reason for preferring QVTo was the
combination of that control and access to the populated target, rather
than sequencing on its own.

This choice makes correct ordering the transformation author's
responsibility. Adding a reference requires its target to be created
first, and adding a value covered by the \texttt{Revision} requires it to
be assigned before hashing. That responsibility was accepted because the
dependencies are known from the deployment design and can be reviewed
together in the calling mappings.

\subsection{The Structure of the Transformation}
\label{sec:structure}

Every derived value must be recorded in a model before code generation.
This allows tests to compare the values with the oracles independently of
the templates that write them to files.

\subsubsection{Flattening Before the Resolution}
\label{sec:twotransformations}

A single transformation from authored model to \texttt{Resolved Deployment}
would work, but a flattening precedes the resolution. The flattening copies
shared declarations down to each \texttt{Process}, including API access and engine \texttt{Grant}s (declared access to a secret of a database or transit engine). For example, a
\texttt{Project} startup budget of 30s reaches every \texttt{Process}
except one that declares a more specific value, such as 20s. Resolution can
then read the selected budget directly from each \texttt{Process}, without
searching its ancestors. QVT specification Section~8.1.13 likewise composes
a preparation transformation before the main one~\cite{qvt13}. However, the
reason for this split is to isolate declaration precedence from deployment derivation. Its cost is an additional model and
the \texttt{EffectiveProject} and \texttt{EffectiveApplication} classes,
whose copying and override behaviour needs its own tests.

\subsubsection{Resolving One Project with All Projects as Input}
\label{sec:perproject}

One resolution over all \texttt{Project}s at once could produce one
\texttt{Resolved Deployment} for the whole estate. Instead, each invocation
resolves one \texttt{Project} into its own model while reading every
\texttt{Project}'s documents from the same input extent. This preserves a
separate output and oracle comparison for each \texttt{Project}, while the
shared input supplies the cluster-wide view needed for dependencies, routes,
and network access. It does not make a \texttt{Project} independently
resolvable: a change elsewhere can affect its output. Values that depend on
all resolved outputs, including the digest over the Vault documents, require
the final pass over those models (Section~\ref{sec:finalpass}). A single
estate-wide output could compute these values in the same invocation but
would combine the output and comparison units.

\subsubsection{Typed Extents}
\label{sec:extentsalternative}

A rule also has to find the run's other documents. An unqualified
\texttt{allInstances()} lookup searches all loaded models, which is problematic when both authored (original) and flattened (copied) \texttt{Process}es are present simultaneously. Instead, the transformation selects roots by type from the
named \texttt{intent} and \texttt{pinned} extents and stores them in
transformation properties such as \texttt{projects} and \texttt{lock}.
Rules navigate from these properties, making their input scope explicit
(Section~\ref{sec:shape}).

\subsubsection{Rejecting Unresolvable Inputs}
\label{sec:abortsalternative}

A default for a value the resolution cannot derive would give a file that
looks valid and deploys the wrong configuration, so the run aborts instead,
through a fatal assertion in an abort query (Section~\ref{sec:aborts}). The
caller then has to handle the failure.
