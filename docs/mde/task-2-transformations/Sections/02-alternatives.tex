KubeOrch comes closest: it turns service links into addresses and ports.
However, it has no shared platform policy or pinned-input model from which
to derive placement, locked images or backups, and no resolved intermediate
model to test. KubeDiagrams could inspect the Task~3 output, while a
KubeOrch-style editor could author \texttt{Project Intent} using the same
Ecore metamodel as the transformation.

\subsection{The Transformation Language}
\label{sec:language}

Task~2 permits ATL or QVT-Operational (QVTo). Both can combine several input
models and maintain source-to-target traces; neither capability alone
distinguishes them. QVT-Relations and Java with a rule library such as SiTra
were also considered as alternative approaches.

QVTo was selected for the dependencies between construction steps. A
\texttt{Process}'s placement combines its declarations with the node
contract; a route refers to an already resolved \texttt{Process}; and an
\texttt{Application}'s \texttt{Revision} hashes its complete resolved
representation. Ordered mapping calls construct the \texttt{Process}es before
their routes, trace lookup reuses those target objects, and an \texttt{end}
section reads the assembled model to compute the \texttt{Revision}. Typed
input extents define the documents searched by OCL queries. This keeps
construction, cross-reference lookup and final derivation in one resolution.

ATL remains a viable alternative. Its matched rules can match several
source elements and resolve references through automatic traces, while
lazy, unique lazy and called rules support explicit invocation. The
distinction is therefore how the final derivation is expressed. In ATL's
usual execution model, target models are write-only: hashing a completed
\texttt{Application} would require deriving its canonical representation
from source helpers or adding a pass that reads the generated model.
QVTo allows the completed target objects to be inspected within the same
transformation. The cost is that mapping order becomes an explicit
responsibility, rather than being delegated to ATL's matched-rule engine.

QVT-Relations can also express a one-way transformation. Its consistency
checking and multidirectional execution are unnecessary here, since the
resolved model is regenerated from intent. QVTo was preferred because the
construction order and the point at which hashing becomes valid can be
stated directly. Java offers the same control and standard debugging tools.
Plain Java would need a trace data structure, whereas SiTra supplies one;
neither lacks the required expressive power. QVTo retains OCL navigation
over the existing metamodels for both constraints and derivations, avoiding
a separate Java rule implementation for this proof of concept. SHA-256
is delegated to a Java black box (Section~\ref{sec:blackbox}).

Speed was not a selection criterion. The compiler, which derives a resolved
model and subsequently generates deployment files, is a proof of concept
for checking the design against the specification's examples. Its design
will later be ported to a general-purpose language such as TypeScript or Rust.

\subsection{The Structure of the Transformation}
\label{sec:structure}

Every derived value must be recorded in a model before code generation.
This allows tests to compare the values with the oracles independently of
the templates that write them to files.

\subsubsection{Flattening Before the Resolution}
\label{sec:twotransformations}

A single transformation from authored model to \texttt{Resolved Deployment}
would work, but a flattening precedes the resolution. The flattening copies
shared declarations down to each \texttt{Process}. For example, a
\texttt{Project} startup budget of 30s reaches every \texttt{Process}
except one that declares a more specific value, such as 20s. Resolution can
then read the selected budget directly from each \texttt{Process}, without
searching its ancestors. QVT specification Section~8.1.13 likewise composes
a preparation transformation before the main one~\cite{qvt13}, but the
reason for this split is to isolate declaration
precedence from deployment derivation. Its cost is an additional model and
the \texttt{EffectiveProject} and \texttt{EffectiveApplication} classes,
whose copying and override behaviour need their own tests.

\subsubsection{Resolving One Project with All Projects as Input}
\label{sec:perproject}

One resolution over all \texttt{Project}s at once could produce one
\texttt{Resolved Deployment} for the whole estate. Instead, each invocation
resolves one \texttt{Project} into its own model while reading every
\texttt{Project}'s documents from the same input extent. This preserves a
separate output and oracle comparison for each \texttt{Project}, while the
shared input supplies the cluster-wide view needed for dependencies, routes
and network access. It does not make a \texttt{Project} independently
resolvable: a change elsewhere can affect its output. Values that depend on
all resolved outputs, including the digest over the Vault documents, require
the final pass over those models (Section~\ref{sec:finalpass}). A single
estate-wide output could compute these values in the same invocation but
would combine the output and comparison units.

\subsubsection{Typed Extents}
\label{sec:extentsalternative}

A rule also has to find the run's other documents. An unqualified
\texttt{allInstances()} lookup does not identify which input model is
intended, particularly when authored and flattened \texttt{Process}es are
both loaded. Instead, the transformation selects roots by type from the
named \texttt{intent} and \texttt{pinned} extents and stores them in
transformation properties such as \texttt{projects} and \texttt{lock}.
Rules navigate from these properties, making their input scope explicit
(Section~\ref{sec:shape}).

\subsubsection{Rejecting Unresolvable Inputs}
\label{sec:abortsalternative}

A default for a value the resolution cannot derive would give a file that
looks valid and deploys the wrong configuration, so the run aborts instead,
through a fatal assertion in an abort query (Section~\ref{sec:aborts}). The
caller then has to handle the failure.
