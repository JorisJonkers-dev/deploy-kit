\section{Alternatives and Justification}
\label{sec:alternatives}

This section answers three questions. Could existing Kubernetes tools replace
the transformation (Section~\ref{sec:existingtools})? Which language should it
be written in (Section~\ref{sec:language})? How should it be structured
(Section~\ref{sec:structure})? It gives the answers in general terms;
Section~\ref{sec:design} gives the detail.

\subsection{Existing Kubernetes Modelling Tools}
\label{sec:existingtools}

Three open-source tools that model Kubernetes applications were reviewed, two of
them graphical. For each, the questions were: can it produce the resolved model
or the files from what an author declares? If not, can it take part in the
pipeline? Table~\ref{tab:tools} gives the answers.

None of the three derives values from what an author declares. KubeOrch comes
closest: its automatic wiring resolves a link between two services to an
address and a port, as the resolution does for a dependency edge. But it has no
platform document, node contract or images lock, so it cannot derive placement,
image digests, backups or network peers, and its result is not a model that a
constraint or an oracle can check. The tools can therefore sit beside the
transformation, not replace it. Two integrations follow from the design:

\begin{itemize}
  \item the resolved dependency edges and network peers are exactly the links a
    KubeDiagrams view of the Task~3 files would draw, so the drawing is a cheap
    visual cross-check of \texttt{dependencies.json};
  \item a graphical editor in KubeOrch's style could write project documents,
    because its models and the Xtext grammar's would be instances of the same
    Ecore metamodel.
\end{itemize}

Neither is built, because neither changes what the transformation must derive.

\subsection{The Transformation Language}
\label{sec:language}

Four languages were candidates: ATL, QVT-Relations, QVT-Operational (QVTo),
and Java, by hand or with a small rule library such as SiTra.
QVT-Relations was dropped first. Its strengths, automatic traces and
synchronisation in both directions, buy nothing for a one-way derivation, and in
published experiments its engine ran out of heap space on larger
models~\cite{amstel2011}. Table~\ref{tab:languages} compares the other three
against what this transformation has to do.

\begin{table}[!htbp]
\centering
\begin{tabular}{>{\raggedright\arraybackslash}p{0.27\linewidth}>{\raggedright\arraybackslash}p{0.20\linewidth}>{\raggedright\arraybackslash}p{0.20\linewidth}>{\raggedright\arraybackslash}p{0.20\linewidth}}
\hline

\hline

  helpers outside the rules & queries, in OCL & methods \\

  order of matched rules and bindings unspecified & explicit, by call order & explicit \\

  implicit, for matched and lazy rules & explicit \texttt{resolveone} through the trace & a trace kept by hand \\

\hline

The deciding property is the shape of the derivations. Most values in a
resolved model do not come from one source element: the eligible machines of a
process depend on the node contract, a route's precedence on the other routes,
and the ingress peers of a process on every process in the cluster that depends
on it. ATL is strongest when one source element maps to one target element,
through matched rules whose order the engine chooses. Here most of the work
would move into helpers and called rules, which is imperative ATL without the
matching, and several values need the rest of the model to exist first. QVTo
makes both visible: the caller decides the order, and every reference from one
created element to another goes through the trace explicitly. Its expressions
are OCL, which the constraints of Task~1 already use. A Java transformation
would be the easiest to debug, but it keeps the trace by hand and hides the
rules in general-purpose code, which practitioners themselves find hard to
maintain for model management~\cite{burgueno2019}.

QVTo was therefore chosen. It is also the second most used transformation
language after ATL, and its users name its maturity and its standard as the
reasons~\cite{burgueno2019}. Speed did not decide the choice: QVTo ran more than
five times slower than ATL in published experiments~\cite{amstel2011}, which is
acceptable for a cluster of about ten projects. The one operation QVTo cannot
express, a SHA-256 hash, comes from a Java black-box library, the mechanism QVT
defines for calling external code (Section~\ref{sec:blackbox}).

\subsubsection{A Lowering Before the Resolution}
\label{sec:twotransformations}

An author may declare a secret, a dependency or a startup budget once for a
whole project, once for an application, or on a single process. The lowering
merges these levels onto each process, so that each process carries everything
that applies to it. If the resolution read the authored model instead, every
rule that reads a process would have to merge three levels again, and could
merge them differently in different rules. With a lowering, each rule reads one
place. A preparation step before the main transformation is also the QVT
specification's own example of composing transformations~\cite[Section~8.1.13]{qvt13};
here the Java pipeline chains the three instead of QVTo's \texttt{access
transformation}, so each can be run and tested on its own.

\subsubsection{One Project per Run, All Projects as Input}
\label{sec:perproject}

The resolution runs once per project, with the other projects as inputs:
\texttt{auth} reads \texttt{data} to find its database's address, and
\texttt{data} reads \texttt{auth} to find who may reach it. One model for the
whole cluster would also work, since QVTo can create several root objects in one
run, but the production implementation and its oracles are per project, and a
project's model is then what its repository publishes. The cost is the one
value that needs every project's output, which the estate pass computes.

\subsubsection{Typed Extents Instead of a Global Scan}
\label{sec:extentsalternative}

A rule could find another document with OCL's \texttt{allInstances()}, as some
cross-document constraints of Task~1 do. That costs a scan of everything loaded
on each evaluation, and gives a result that depends on which files happened to
be loaded together. The transformation avoids both: each input is selected
once, by type, from two extents that hold exactly the documents of the run, and
every rule navigates from there (Section~\ref{sec:interface}). The constraints still use \texttt{allInstances()}, guarded so that they hold
over a file read alone. The pipeline therefore checks each file alone and then
the whole set of a run together, and the platform document is always in that
set, so a guarded constraint never skips in a run. Moving those
constraints onto one root object that holds the set, so that they too navigate
instead of scan, is decided but not yet built (Section~\ref{sec:limitations}).
