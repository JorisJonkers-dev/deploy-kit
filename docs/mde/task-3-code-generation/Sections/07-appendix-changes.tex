\section{Changes to the Task 1 Metamodels and Task 2 Transformations}
\label{sec:appendix}

This appendix lists changes to the Task~1 metamodels and Task~2 transformations
in the Task~3 pipeline, organised by artefact. The baseline is the Task~2
submission's metamodel appendix and design section. These describe three
QVT-Operational transformations (lowering, resolution and the estate pass
over the Resolved Deployments) and the Task~1-to-Task~2 metamodel changes.
Each table row identifies a change, its affected classes and features, and its reason.

Production deployment revealed cases requiring model changes. The tables group
these changes by theme. Changes specific to the model-driven implementation
form a separate group. The
change set was derived from the repository's git history rather than a
comparison of complete models, so each row summarises a commit's effect.

The Project Intent
metamodel, which also holds the Platform Intent classes, has 129 classes and
419 features, the Resolved Deployment metamodel 133 classes and 594 features,
and the Pinned Inputs metamodel 18 classes and 60 features. The resolution
transformation has 4212 lines, 10 mappings and 300 queries, and the lowering
has 474 lines and 54 mappings, compared with about 1700 and 340 lines in the
Task~2 design section. The 134-line estate pass was removed. The Acceleo
module has 3607 lines.

\subsection{Source Metamodel (Project Intent)}
\label{sec:appendix-source}

The source metamodel defines what an author writes in a Project's files.
Figure~\ref{fig:mm-source} shows its Project Intent part. Changes fall into five
themes: how a \texttt{Process} reaches platform services, how it receives secrets,
the identity and placement constraints checked by the model, further forms of
\texttt{Process}, and the exposure, sign-in and observation of an
\texttt{Application}. The Platform Intent classes are in
the same \path{project-intent.ecore} file, and Section~\ref{sec:appendix-platform}
covers them separately.

\subsection{Platform Intent}
\label{sec:appendix-platform}

The platform team writes one Platform Intent for the estate. It defines choices
unavailable to Projects: privileged roles, engines and their catalog methods,
images for platform components, resources available to Processes and
the policies limiting their use. Figure~\ref{fig:mm-platform} shows its classes.
Its metamodel is the Platform part of \path{project-intent.ecore}; its grammar is
\path{PlatformIntent.xtext}.

\begin{figure}[!htbp]
\centering
\includegraphics[width=\linewidth, keepaspectratio]{Figures/mm-platform}
\caption{The Platform Intent Metamodel as Submitted}
\label{fig:mm-platform}
\end{figure}

Platform Intent changed in two ways. First, the eight privileged-role fields
now name both a Project and an Application, breaking compatibility with every
document that sets them. Second, it gained policies from
transformations or Project files: the VPN image, GPU resource names, library
grants and each engine's catalog method.

\subsection{The Transformations}
\label{sec:appendix-transformations}

Task~2 used lowering, resolution, an estate pass over several Resolved Deployments,
and rendering. The pipeline now lowers, resolves and renders. Resolution plans
the removed estate pass's values per Project. This follows the rule that a Project
owns every object it delivers (\path{spec/v1/20-resolved-deployment.md}); as a
consequence, each Project plans shared values separately.

\texttt{ModelDiff} for all 36 example Project files (2564 objects; 51 of
its 54 rules match an object). Times are medians with interquartile ranges over

\section{The TypeScript Production Implementation (Supplementary)}
\label{sec:appendix-production}

This supplementary appendix records the oracles' source and how the model reaches

\subsection{The Source of the Oracles}
\label{sec:appendix-oracles}

The production implementation, in TypeScript under \path{src/}, compiles the same
model for production use. It renders the same cases, and
\path{test/model/render.test.ts} compares its output with the same committed files.
Its serialiser writes YAML with \texttt{version: "1.1"}
(\path{src/infrastructure/serializer.ts}); the templates use the same quoting rules
(Section~\ref{sec:design}). The repository forbids generating either implementation
from the other, and regenerating an oracle in CI. Disagreement indicated a defect in one implementation: each time the production implementation
gained a rule, the model-driven implementation adopted it until both matched the
oracles.

This independence is partial: one author wrote both implementations, and the
committed trees changed in the same commits as an implementation. Agreement rules
out errors made by only one implementation, not a shared misreading of the
specification; the external checks of Section~\ref{sec:evaluation} test Kubernetes'
requirements rather than the specification. The Pod Security check permits one
named exception: the VPN sidecar.

\subsection{From a Change to Production, Today and in Future}
\label{sec:appendix-delivery}

\begin{figure}[!htbp]
\centering
\includegraphics[width=\linewidth, keepaspectratio]{Figures/delivery-paths}
\caption{Delivery Today and Its Future Direction}
\label{fig:delivery-paths}
\end{figure}

Figure~\ref{fig:delivery-paths} shows two paths from a merged change to a serving
release. \textbf{Today} (\path{spec/v1/55-delivery.md}), delivery uses a pull model. A
Project's CI validates its Intent and pins its images. Composition renders the
estate once and publishes each Project's share as one signed OCI artefact,
named by digest. A deployment is a commit changing the Project's digest pin in the estate
repository. Its history is the deployment log. Flux pulls
the artefact, verifies its signature and applies it, and Flagger switches
traffic once the Release Gate allows it. Nothing pushes to the cluster.

In the \textbf{future direction}, which is being refined in estate-kit, the repository that
succeeds deploy-kit (Section~\ref{sec:outlook}), Project CI contacts a
Conductor and keeps a bi-directional event stream open until the rollout serves traffic, is held
or is refused. A self-hosted OCI registry stores the output. An Applier in its own
process replaces Flux: it pulls the rendered output by digest, verifies it, applies
it in ordered steps (definitions and namespaces, secrets and grants, migrations,
workloads, routes) and reports each object's status. Flagger remains as a deployment
step driven by the Applier, and its outcome reaches Project CI through the same stream.

Both paths retain the model and its oracles. The Resolved Deployment records
every decision; the applier and transport of rendered files change.
