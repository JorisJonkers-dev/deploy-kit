\section{Example Models}
\label{sec:examplemodels}

Five example models instantiate the source metamodel, each testing a different
part of it (Table~\ref{tab:examples}). Appendix~\ref{sec:handin} gives their
paths, and Section~\ref{sec:constraints} describes the rejected models.

\begin{table}[!htbp]
\centering
\small
\begin{tabular}{>{\raggedright\arraybackslash}p{0.16\linewidth}>{\raggedright\arraybackslash}p{0.76\linewidth}}
\hline
\textbf{Example} & \textbf{What it tests} \\
\hline
minimal & The smallest complete model: one project, one application, one
  process, and only required values. \\
auth & Two \texttt{continuous} processes in one application, so the release gate has two
  members and its deadline is the maximum over the members. It also has a
  managed migration, because the application uses a database. \\
data & Several applications in one project share a namespace. Each volume's
  durability class determines its backup plan. \\
knowledge & Two applications in one project, because their \texttt{cutover}
  values differ: a \texttt{continuous} API that migrates the project's schema
  with a changelog, and an \texttt{interrupted} worker with a volume and no
  migration of its own. It also has dependencies between applications, secrets
  shared at project level, and an exposure whose routes have different
  audiences. \\
delivery & Two applications of the delivery machinery: Flagger and the release gate.
  Their processes are \texttt{continuous} but are updated in place instead of
  switched blue/green, because the release gate cannot control its own
  release. \\
\hline
\end{tabular}
\caption{The Example Models and What Each Tests}
\label{tab:examples}
\end{table}

Each example has three stages: the authored project file, the resolved model,
and the generated file tree. Appendix~\ref{sec:appendix} follows three examples
through these stages.

\subsection{The Minimal Model}

The minimal model is considerably shorter than the current hand-written file for
the same deployment. It declares no rollout strategy, resource limits, security
context, labels, selector, namespace, probe timings or instance count. Each of
these is derived from a declared value, set by platform policy, or rejected, so
the model shows the minimum an author has to write.

\subsection{Example Target Models}

For the minimal example, the resolved model that the Task 2 transformation must
produce was written and reviewed by hand, as
\texttt{minimal.resolveddeployment}. It is the expected output of that
transformation and the first input for the Task 3 templates, so both tasks can
be tested before either is complete.
