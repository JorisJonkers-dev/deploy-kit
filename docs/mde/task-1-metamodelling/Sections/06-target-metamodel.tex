\section{The Target Metamodel}
\label{sec:targetmetamodel}

The target metamodel is \texttt{model/resolved-deployment.ecore} in the archive.
Task 2 produces its instances. Task 3 generates files from them. A resolved
model records platform decisions, typed resources and output paths.

\subsection{Required Content}

Generators use the resolved model (Section~\ref{sec:stagecontent}).

\textbf{Decisions.} Derived values include edge tiers, eligible machines,
process identity, image digests, probe timings, backup plans and network peers.
\emph{Switchover} specifies how a new process version replaces the old:
\texttt{blue-green}, \texttt{stop-start} or, for delivery machinery,
\texttt{rolling}.

\textbf{Order and atomicity.} \emph{Reconcile units} group objects Flux applies
together. Dependency edges order these groups. For a blue/green application,
the \emph{release gate} controls when the new version receives traffic. Its
inputs include members, checks, an interval and a deadline.

\textbf{Release identity.} An application's \emph{revision} hashes its resolved
element, excluding the revision field. Migrations and release gates use that
revision to identify the same release.

\textbf{Provenance.} A run hash and input digests identify project documents,
platform policy, the machine contract, pinned image digests and observed cluster
state. Identical inputs must produce identical output.

A \texttt{ResolvedApplication} also forms the projection published to its
repository. Only that published projection has separate provenance.

\texttt{ReleaseGate} is absent when no process switches blue/green. An
interrupted application stops before the new version starts. The delivery
machinery updates in place.
\texttt{ResolvedMigration} records changesets that cannot run in a transaction
and cannot be undone automatically. Migration identity, owner role and deadline
follow from the application and platform document.

The \texttt{cutover} and \texttt{switchover} of a \texttt{ResolvedProcess} are
unset for a prepare process, which replaces no running version.

\subsection{The Path Plan}

The \emph{path plan} assigns each generated object to a generator and output
path (Section~\ref{sec:stagecontent}). Earlier generator-chosen paths duplicated
a group object across applications and placed a cluster object in an arbitrary
namespace. The path plan lets the platform detect output-path collisions
before generation.

\subsection{The Generated Resources}
\label{sec:generatedresources}

Six generators produce workloads, network policy, monitoring, edge routing,
secret-store policies and secret delivery (Table~\ref{tab:scope}). A
\emph{Canary} lets Flagger switch traffic to a new version.

\textbf{Typed resources.} The output consists of Kubernetes, Flux, Flagger,
Traefik and Vault files. Decision classes specify their content. Typed resource
classes specify output paths and generators. They include
\texttt{WorkloadFile}, \texttt{SwitchoverFile}, \texttt{NetworkPolicyFile},
\texttt{MonitorFile} and \texttt{IngressRouteFile}. The remaining types are
\texttt{SecretFile}, \texttt{IdentityFile}, \texttt{NamespaceFile} and
\texttt{IndexFile}. A model-to-text template writes each typed resource.

\subsection{Keeping Target Field Names Out of the Model}

\texttt{SwitchoverFile} records a blue/green switch
(Section~\ref{sec:naming}). Its generator writes a Canary. The model also records
hardening, writable paths and middleware steps instead of target syntax.
