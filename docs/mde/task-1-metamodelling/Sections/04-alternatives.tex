\section{Alternatives and Justification}
\label{sec:alternatives}

The starting point is how the cluster is configured today: Kubernetes files
written by hand in each application's repository. The related values between
services make these files hard to keep consistent, and each application repeats
the same deployment behaviour. The other alternatives either keep these
problems or move them elsewhere. This section first compares them
(Section~\ref{sec:alternativesconsidered}), and then gives the decisions of the
chosen solution in general terms (Section~\ref{sec:decisions}).
Section~\ref{sec:design} describes the resulting classes in detail.

\subsubsection{A Third Metamodel for the Generated Files}
\label{sec:thirdmetamodel}

A third metamodel could support structural output checks, but a maintained copy
of the target schema could drift. It adds no constraint beyond the resolved
metamodel. The resolved metamodel contains typed resource classes
(Section~\ref{sec:generatedresources}).

\subsubsection{Grammar First or Metamodel First}
\label{sec:grammarfirst}

Source models have two serialisations: YAML for authors and XMI for Eclipse.
If the YAML grammar inferred the metamodel, it would determine the concepts in
both forms. Defining Ecore first gives both serialisations the same classes.

\subsubsection{One Resolved Model, or One Per Application}
\label{sec:oneresolved}

The resolved model covers all applications. Edge routing, deployment order and
reverse dependencies require a cluster-wide view. Reverse dependencies identify
which applications depend on a given application. Separate per-application
computations could disagree or omit values.

Each repository receives a \emph{projection}: its application's part of the
resolved model, selected by filtering.
