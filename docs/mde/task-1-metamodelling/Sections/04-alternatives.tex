\subsection{A Third Metamodel for the Generated Files}
\label{sec:thirdmetamodel}

A third metamodel would let the generated output be checked structurally instead
of as text. As a hand-maintained copy of the target schema, however, it could
drift, and it would add no constraint beyond those of the second metamodel. The
generated files are therefore compared as text with reviewed expected output,
and validated against their own schemas. The typed target resources are classes
in the second metamodel (Section~\ref{sec:generatedresources}).

\subsection{Grammar First or Metamodel First}
\label{sec:grammarfirst}

The source language has a textual syntax, so a grammar could have defined it,
with the metamodel inferred. The production implementation, however, parses a
different serialisation of the same language. If a grammar defined the language,
the two syntaxes would agree only by chance. With the metamodel first, both are
checked against one structure, which is exported as a machine-readable
description for testing both implementations.

\subsection{One Resolved Model, or One Per Application}
\label{sec:oneresolved}

The resolved model covers all applications in one document, because some values
cannot be computed for one application alone. Examples are which edge entry
point serves a hostname, the order in which groups of objects are applied, and
what an application derives from the applications that depend on \emph{it}. A
per-application model would compute these inconsistently or omit them.

Each application's repository receives a \emph{projection}: the part of the
cluster-wide model that belongs to that application. It is obtained by
filtering rather than by a separate computation, so the two cannot disagree.
