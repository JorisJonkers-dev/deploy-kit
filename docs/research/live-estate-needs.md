# What the live estate needs from deploy-kit

An inventory, Application by Application, of what the running estate uses, how
much of it `spec/v1` models and `src/` renders, and what stands between each
Application and its handover to the estate path. Researched 2026-10-09 for
JorisJonkers-dev/deploy-kit#343, on the map JorisJonkers-dev/deploy-kit#341;
see [the index](README.md#method) for the markers used. It recommends no
handover order: that is JorisJonkers-dev/deploy-kit#349's decision.

The fleet-infra feature counts below come from parsing every YAML document under
`cluster/flux/apps/` and listing, per directory, the object kinds and the pod
fields each uses (containers beyond the first, init containers, volume sources,

reading the directory named.

## Findings

**The deploy-config-schema descriptor deploys nothing; fleet-infra's
hand-written tree does.** Nine first-party repositories carry a
`deployment.jorisjonkers.dev/v2` descriptor at `platform/deployment.yml` (24 to
78 lines; stalwart-provisioner keeps its own at `deploy/deployment.yml`). Each
declares a namespace, workloads, health checks, routes and rollback retention,
and nothing else: none declares a volume, a secret, a dependency, resources,
replicas or placement, though the v2 schema has a field for each but the
dependency (`src/deployment/v2-model.ts`, `WorkloadV2`). A tagged release renders the
descriptor into a deploy artifact, `ghcr.io/jorisjonkers-dev/<repo>:deploy-<version>`,
whose fragments (an edge catalog entry, a Gatus endpoint, an image digest)
fleet-infra only **compares** against its own tree
(`scripts/validate/fragment-drift.sh`: "It does not generate anything and cannot
deploy anything"). The live objects are hand-authored under
`fleet-infra/cluster/flux/apps/`. fleet-infra's own plan says so: "`cluster/flux`
is **hand-authored**", 271 YAML files of which none carried the compiler's
generated-file header when it was written (`DEPLOY-PRODUCTION-PLAN.md`). The
plan names five files the toolkit's adapters did produce (two edge catalogs, two
IngressRoute files and the Gatus endpoints); the two IngressRoute files are gone
and every route is now a hand-written file beside its Application. Of the 409
YAML files under `cluster/` today, only Flux's own installer says it is
generated, and none names deploy-config-schema
(`grep -rlI -i 'generated by' cluster/`, `grep -rlI deploy-config-schema cluster/`).
The five `homelab-collections`
documents are a catalog over those same files: each service lists the
fleet-infra paths it stands for under `sourceManifests`. So what an Application
needs has to be read from fleet-infra, and the descriptor column of the table
below records how little of it the descriptor states.

**The handover ledger does not name every live Project.** `handover.legacy`
lists thirteen Projects (`edge`, `secrets`, `observability`, `data`, `auth`,
`knowledge`, `agents`, `media`, `mail`, `notes`, `app`, `automation`,
`utility`; estate `platform.intent.yml`). The cluster also runs `grimoire` and
`tribelt` (each in a namespace of its own name), `overleaf` (`latex-system`) and
the knowledge platform (`knowledge-platform-system`, whose model is the worked
[`knowledge-platform`](../../spec/v1/examples/knowledge-platform/knowledge-platform.project.yml)
example). A project file for any of the four is `E_HANDOVER_UNLISTED` until the
ledger lists it ([chapter 14](../../spec/v1/14-platform-intent.md#handover-ledger)).
Six foundation components run from HelmReleases that no platform project file
declares: cert-manager, external-dns, MetalLB, Reloader, the NVIDIA device
plugin and the Vault Secrets Operator (`kubectl get helmrelease -A`; the estate's
`platform/` holds `edge`, `observability` and `secrets` only).

**`<project>-system` does not reproduce the live namespaces.**
[Chapter 60](../../spec/v1/60-setup.md#adopting-a-live-application) says it
"reproduces all ten live namespaces and renames nothing". The cluster has 29
namespaces, and seven that hold an Application the model would own are not of
that form: `grimoire`, `tribelt`, `observability`, `ingress-system`,
`ingress-lan-system`, `vso-system`, and Vault's `data-system` (the model puts
Vault in `secrets-system`). For those, handover is a namespace move, not the
in-place takeover [chapter 60](../../spec/v1/60-setup.md#handing-over-one-project-at-a-time)
describes. JorisJonkers-dev/deploy-kit#310 and JorisJonkers-dev/deploy-kit#316
are this finding for the edge and for Vault.

**`<project>_db` renames three Projects' databases.**
[Chapter 16](../../spec/v1/16-dependencies.md#the-database-catalog) fixes a
Project's database as `<project>_db`, "the spelling the live estate already
uses". It matches `auth_db`, `knowledge_db`, `agents_db`, `grimoire_db` and
`tribelt_db`. It does not match `outline_db` (Project `notes`), `n8n_db`
(`automation`), or `hindsight_db` and `knowledge_platform_db`, two databases in
the one Project `knowledge-platform`, whose derived name would carry a hyphen
(`grep -rhoE '[a-z0-9_]+_db' cluster/flux/apps`). `mem0_db` and `assistant_db`
are named by reconcile Jobs and belong to no live Application.

**The estate delivers database credentials in a way the model does not.**
grimoire, tribelt, outline and n8n receive their Postgres credential as
environment variables from a `VaultDynamicSecret` (fleet-infra
`stateless/<app>/vault-secrets.yaml`). The model delivers the credential an
edge derives `self`, so the Process logs in to Vault itself
([chapter 10](../../spec/v1/10-project-intent.md#migration)), while
[chapter 16](../../spec/v1/16-dependencies.md#the-database-catalog) says `vso`
"projects it with the `VaultDynamicSecret` it already emits". `src/` renders no
`VaultDynamicSecret` (`grep -rn VaultDynamicSecret src` finds nothing), and a
`database` grant is `self` only (`E_NON_KV_DELIVERY`). Pods in eleven
directories (among them auth-api, agents-api, knowledge-api,
knowledge-ingest-worker, lightrag, the downloads pod and Postgres's own Jobs)
read Vault through the Vault Agent injector's annotations, which the model has
no word for, and agents-api reads a **RabbitMQ** dynamic credential,
`rabbitmq/creds/app-consumer`, from an engine the grant union does not have
(kv, database, transit;
[0029](../adr/model/0029-a-grant-is-a-union-on-engine.md)). The one shared
`secret/data/platform/postgres` is named 66 times in the tree, where the model
derives one data role per consuming Project.

**Today's shapes trip four refusals.** Applied to what runs now:

- `E_DUPLICATE_HOST` ([chapter 10](../../spec/v1/10-project-intent.md#what-is-checked)):
  eight media hosts, `hermes.jorisjonkers.dev` and `agents-ws.jorisjonkers.dev`
  are served on both the public and the LAN tier under one hostname (fleet-infra
  `media/*/ingressroute-*-lan.yaml`, `agents/hermes/ingressroute-lan.yaml`,
  `stateless/agents-api/ingressroute-agents-ws-lan.yaml`). The model allows an
  Application two exposures, never two with one host.
- `E_HARDENING_UNMET` ([chapter 10](../../spec/v1/10-project-intent.md#writable-paths-are-declared-not-exempted)):
  jellyfin's init container runs as root; the downloads pod's VPN sidecar
  (gluetun) adds `NET_ADMIN`; two hermes containers run as root and one adds
  `CHOWN`, `DAC_OVERRIDE`, `FOWNER`, `SETUID` and `SETGID`; an agents-api
  container runs as root with `CHOWN`.
- `E_PRIVILEGED_PORT_UNDER_NONROOT` ([chapter 10](../../spec/v1/10-project-intent.md#a-privileged-port-needs-the-capability-that-binds-it)):
  stalwart binds 25, 110, 143, 465, 587, 993 and 995 through `hostPort`;
  AdGuard binds 53 and 80; auth-ui and agents-ui listen on 80.
- `E_PROCESS_RBAC_GRANT` ([chapter 10](../../spec/v1/10-project-intent.md#kubernetes-api-access)):
  agents-api and the agents project's `kubernetes-mcp-server` hold Kubernetes
  API access through their own ServiceAccounts (`agents/rbac/`,
  `agents/mcp/kubernetes-mcp-server/cluster-role.yaml`), and the Platform document admits only `flagger`,
  `release-gate` and `collector` (`apiAccess.holders`).

**Ten kinds of need appear in no chapter.** Listed in full under
[Features the estate uses that the spec lacks](#features-the-estate-uses-that-the-spec-lacks):
host paths, host ports and LoadBalancer Services, a GPU device request and its
runtime class, scheduled jobs, init containers, Pods created at runtime,
internet egress, MongoDB and S3 (Garage) as engines, priority classes, and a
Service fronting an off-cluster host.

**`src/` renders the application lifecycle and little around it.** It renders
`lifecycle: application` Processes only: a `job` or `prepare` Process stops the
render (`src/adapters/kubernetes/render.ts`, `notYet`). Byte-for-byte oracles
exist for `minimal`, `data`, `auth`, `delivery`, `knowledge-platform` and
`_estate` (`test/model/render.test.ts`); `knowledge`, `edge` and
`observability` have none. No Middleware object, Gatus endpoint, edge catalog,
`VaultDynamicSecret` or StatefulSet is rendered, a redirect stops the render
(`src/adapters/traefik/render.ts`), and the Vault policy adapter renders the
`read` access tier only (`src/adapters/vault-policy/render.ts`).

**Nothing has been handed over yet, and the estate path does not apply.** The
first composition's units are not ready: `estate-vso-secrets` and
`apps-delivery` report `False` (`kubectl get kustomizations -A`), because the
Vault policy job targets `secrets-system`, which does not exist
(JorisJonkers-dev/deploy-kit#316). The first handover, `app`
(JorisJonkers-dev/home-portal#70), additionally waits on
JorisJonkers-dev/deploy-kit#310, JorisJonkers-dev/deploy-kit#311 and
JorisJonkers-dev/github-workflows#135.

## How a descriptor is discovered today

- **First-party repositories** keep `platform/deployment.yml`,
  `platform/images.lock.json` and `platform/production.env`. The tag-triggered
  `publish.yml` builds the image, writes the lock and renders the deploy
  artifact (home-portal `.github/workflows/publish.yml`). home-portal's runs a
  second path beside it, publishing a deploy-kit Intent Fragment from
  `deploy/app.project.yml`.
- **Third-party services** are described in `homelab-collections`
  (`deployment.jorisjonkers.dev/collection/v1`), indexed by
  `deploy-config-schema collections index` (deploy-config-schema `README.md`).
- **fleet-infra** is what applies. `fragment-drift.sh` walks every first-party
  image pin in `cluster/flux`, fetches the matching deploy artifact anonymously
  from GHCR, and fails on a digest, edge host or Gatus probe that disagrees,
  minus the entries in `catalog/accepted-fragment-drift.yml`.
- The descriptors have drifted from the tree they describe: the `utility`
  collection lists `adguard` at `utility-system/adguard/` and `wolfmanager`,
  while fleet-infra runs `adguard-ha` (two Deployments) and no wolfmanager; the
  stalwart-provisioner descriptor declares `kind: job`, while fleet-infra runs
  it as a sidecar of the stalwart pod (`mail/stalwart/deployment.yaml`).

## Features the estate uses that the spec lacks

Each is used by a live Application and named by no chapter of `spec/v1`
(searched by `grep -il` over `spec/v1/*.md` for each term):

1. **Host paths.** Media (bazarr, radarr, sonarr, jellyfin, jellyseerr, immich,
   downloads) mount `/srv/media/*` and `/var/lib/personal-stack/media/*`; tempo
   mounts its generator WAL. A volume in the model is a claim.
2. **Host ports and LoadBalancer Services.** stalwart's eight mail ports bind on
   the node through `hostPort`; AdGuard's DNS is a MetalLB LoadBalancer on TCP
   and UDP 53.
3. **A GPU device request and runtime class.** immich machine learning and
   jellyfin request `nvidia.com/gpu` under `runtimeClassName: nvidia-cdi`. The
   `gpu` dimension decides eligibility; nothing derives the request.
4. **Scheduled jobs of an Application's own.** Nine CronJobs run live
   (`kubectl get cronjob -A`); three are backups the model derives, and six are
   not: `agents-kb-curator-triage`, `agents-kb-curator-weekly`,
   `agents-kb-install`, `agents-refresh-ping`, `garage-asset-sync` and
   `vault-metrics-token-renewal`. JorisJonkers-dev/deploy-kit#236 asks for the
   lifecycle.
5. **Init containers.** auth-api, agents-api, ollama, hermes, basic-memory,
   downloads, jellyfin and AdGuard run them. Chapter 10 rules out only a
   root-capable one for volume ownership.
6. **Pods created at run time.** agents-api creates agent-runner Pods, their
   Services and claims through the Kubernetes API.
7. **Internet egress.** tribelt, the knowledge platform, auth-api's agent
   download and the downloads VPN all call out (JorisJonkers-dev/deploy-kit#270).
8. **MongoDB and S3 (Garage) as engines.** `engine` is `postgres`, `rabbitmq`,
   `valkey` or `files` (`src/model/vocabularies.ts`); grimoire needs S3.
9. **Priority classes.** `platform-data` and `platform-critical-app`
   (`data/priorityclasses.yaml`) are named by seventeen objects
   (`grep -rn priorityClassName cluster/flux/apps`), Vault's chart values among
   them.
10. **A Service fronting an off-cluster host.** `ollama-heavy` is a selectorless
    Service with hand-written Endpoints; a provider gives an edge an address but
    renders no Service.

Two more are in the spec but in a shape the estate does not have: a sidecar
"three times in this estate" ([chapter 10](../../spec/v1/10-project-intent.md#sidecars))
where six pods carry one or more (postgres, valkey, basic-memory, karakeep,
stalwart, downloads), and a weighted scheduling preference, node or pod, found
in ten Deployments (`grep -rl preferredDuringScheduling cluster/flux/apps`),
which [chapter 10](../../spec/v1/10-project-intent.md#what-layer-1-may-never-contain)
forbids outright.

## Spec features no Application uses

Each is specified, and nothing live uses it today:

- **`audience: internal`.** The Platform document's tiers carry `anonymous`,
  `authenticated` and `lan` only (estate `platform.intent.yml`), so a route of
  that audience would be refused for want of a tier.
- **`migration` with a `changelog`.** No live Application migrates through the
  platform's runner; every one that migrates does so itself. auth is the first
  planned user (JorisJonkers-dev/auth-api#80).
- **`lifecycle: prepare`.** No live workload is a forward-only step before a
  release; the one-off Jobs live are database setup, which the catalog
  replaces, and a bootstrap.
- **The `disk` placement dimension.** No live selector names a disk medium;
  media placement selects the `samba` capability.
- **`blue-green` switchover and the Release Gate.** Flagger is not running
  (`kubectl get deploy -A` shows none), so no live Application switches this
  way; every one the render does not class as machinery will.
- **`self-roll` access.** No live writer patches a value it also reads
  (Unverified: found by reading Vault paths in the tree, not Vault's own
  policies).
- **The Stable Address and the Move** ([chapter 16](../../spec/v1/16-dependencies.md#the-stable-address),
  [chapter 55](../../spec/v1/55-delivery.md#moves)). Specified ahead of both
  implementations (JorisJonkers-dev/deploy-kit#324).

## Not verified

- **Live state beyond `kubectl get`.** Object specs were read from fleet-infra,
  not the cluster; fleet-infra's own `docs/live-divergence.md` last compared the
  two on 20 August 2026.
- **Which Project the five HelmRelease foundation components belong to.** No
  document assigns them; the `edge` attribution above is by function only.
- **Whether immich's Postgres image fits the `postgres` engine's backup
  method.** It carries the vectorchord extension; the engine catalog was not
  tested against it.
- **The Vault policies themselves.** Paths were read from annotations and
  VaultStaticSecret objects in fleet-infra; Vault's policies and roles were not
  read.
- **Repositories outside this search.** Descriptors were found with
  `gh search code --owner JorisJonkers-dev --filename deployment.yml` and by
  listing the tree of every repository that could deploy; a descriptor in an
  unindexed path would be missed.
