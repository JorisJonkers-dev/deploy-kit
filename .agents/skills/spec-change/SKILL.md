# Spec change

`spec/v1` is normative for the model
([`CONTEXT.md`](../../../CONTEXT.md#the-three-model-pipeline)); an edit to it
is never a documentation-only edit. Treat every item below as one change, not
a sequence to land separately: a chapter edit with no matching oracle update
is a parity break waiting for whichever implementation runs its test suite
next.

## What one spec change touches

- **The chapter itself.** Adding or renaming a `## ` heading breaks the
  anchor check for any ADR whose `normative:` pointer names it
  ([`docs/architecture.md`](../../../docs/architecture.md)'s own opening
  paragraph states the same rule for its own chapters); update the ADR's
  pointer in the same change, never after.
- **The ADRs that point at it.** An ADR justifies; the spec is normative.
  Where a change makes an ADR's `## Why` stale, fix the ADR, not the spec.
- **`CONTEXT.md`.** A renamed or new concept gets its one entry there, in the
  section matching its layer, with no field list or rationale duplicated
  from the chapter.
- **The worked examples**, under `spec/v1/examples/<case>/`. A field that
  changes shape or a rule that changes behaviour needs an example that
  exercises it, positive (`expected/`) or negative (`refusals/` or
  `negative/`).
- **The rendered trees and oracle files**: `expected/intent.json`,
  `expected/dependencies.json`, `expected/resolved.json`,
  `<input>.diagnostics.json`, `rendered/`, `expected/descriptor.json`.
  Written and reviewed by hand, never regenerated by CI
  ([`docs/architecture.md#the-parity-contract`](../../../docs/architecture.md#the-parity-contract)).
  A tool may propose a candidate; the committed file is the reviewed copy of
  it, canonical JSON (RFC 8785), byte for byte.
- **The diagrams**, under `spec/v1/diagrams/`: one drawn SVG per chapter, the
  editable draw.io source embedded, one palette, colour carrying the layer.
- **Both implementations' declarations.** While `emf/` exists, a model
  change lands in the TypeScript production implementation and the
  model-driven implementation under `emf/` in the same pull request
  ([`AGENTS.md`](../../../AGENTS.md#boundaries)), each tested against the
  oracle files above separately; neither is generated from the other, and
  neither regenerates an oracle.

## Steps

1. Read the chapter and every ADR whose `normative:` pointer names it, so the
   edit is made once, in the place that is actually normative.
2. Make the wording change, keeping every `## ` heading an existing pointer
   needs, or updating the pointer in the same commit if a heading moves.
3. Update or add the worked example(s) the change bears on, and hand-write
   the oracle files it touches.
4. Update both implementations' declarations (while `emf/` exists), against
   the same oracle files.
5. Run `npm run lint:adrs` and `npm run lint:links`; while `emf/` exists,
   also `node scripts/lint-adrs.ts emf` and `./mvnw -B -ntp verify` inside
   `emf/`.
